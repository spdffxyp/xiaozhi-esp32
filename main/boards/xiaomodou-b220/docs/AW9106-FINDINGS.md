# AW9106B 与 B220 的 I2C 总线

由用户在 PCB 上发现 **AW9106BTQR** 引出，回固件里一对，整条 I2C 总线全部落地。

---

## 1. 结论速览

| 项目 | 值 | 依据 |
| --- | --- | --- |
| 芯片 | **AW9106BTQR**（艾为 AWINIC，6 通道 LED 驱动 + GPIO 控制器，I²C） | PCB + 固件驱动 |
| 7 位从机地址 | **0x5B**（写 `0xB6` / 读 `0xB7`） | 固件全部写操作目标地址 = 91 = 0x5B；与规格书 AD0/AD1 都拉高一致 |
| 总线 | **I2C0**，主模式，**100 kHz** | `i2c_master_cmd_begin(port=0, …, 1000)`；配置结构体 `clk_speed = 100000` |
| **SDA** | **GPIO18** | `i2c_config_t.sda_io_num = 18` |
| **SCL** | **GPIO23** | `i2c_config_t.scl_io_num = 23` |
| 内部上拉 | sda/scl 均使能（=1） | 同一结构体 |
| 固件驱动 | tag `"aw9106"`；写 helper `0x40207770`、读 helper `0x40207808`、`chip_aw9110b_init` `0x402078dc` | 字符串交叉引用 |

---

## 2. 证据链（两条独立路径互相印证）

**路径 A —— 用「时钟魔数」扫数据段**

我之前扫 DROM/DRAM 找外设配置结构体时，在 `0x3f402118` 命中过一个 100 kHz 的结构体：

| 偏移 | 值 | 含义 |
| --- | --- | --- |
| +0 | 1 | `i2c_mode_t` = I2C_MODE_MASTER |
| **+4** | **18** | **sda_io_num** |
| +8 | 1 | sda_pullup_en |
| **+12** | **23** | **scl_io_num** |
| +16 | 1 | scl_pullup_en |
| +20 | 100000 | clk_speed = 100 kHz |

**路径 B —— 从 IDF 驱动代码反推字段布局**

`i2c_param_config`（`0x402343dc`）内部会调用 `i2c_set_pin`，调用点在 `0x4023446f`：

```
40234464: l32i a14, a3, 16    ; scl_pullup_en  = cfg+16
40234467: mov.n a10, a2       ; i2c_num
40234469: l32i.n a13, a3, 8   ; sda_pullup_en  = cfg+8
4023446b: l32i a12, a3, 12    ; scl_io_num     = cfg+12
4023446d: l32i a11, a3, 4     ; sda_io_num     = cfg+4
4023446f: call8 i2c_set_pin
```

两条路推出的字段偏移与数值完全一致 → **SDA=18、SCL=23、100 kHz** 可以确定。

**器件地址**：固件里所有 AW9106 写操作的第一实参都是 `movi.n a10, 91`（0x5B），
写在总线上的字节是 `(91 << 1) = 0xB6` = 写地址；读 helper 用 `0xB7`。
对照规格书「AD0/AD1 决定地址 bit1/bit2，两者都高 → 0xB6/0xB7」，**在位址上完全对上**。

## 3. 固件里还原出的 AW9106 初始化序列

`chip_aw9110b_init`（`0x402078dc`）按顺序写（器件 0x5B，每次 1 字节）：

| 寄存器 | 值 | AW9106 名称 | 含义 |
| --- | --- | --- | --- |
| 0x7F | 0x00 | `RESET` | 软件复位 |
| 0x11 | 0x10 | `CTL` | 电流大小设定 |
| 0x12 | 0x02 | `GPMD_A` | A 组模式 |
| 0x04 | 0x00 | `GPIO_CFG_A` | A 组配置为输出 |
| 0x02 | 0x00 | `GPIO_OUTPUT_A` | A 组输出值 0 |
| 0x13 | 0x00 | `GPMD_B` | B 组设为 LED 模式 |
| 0x20–0x25 | 0x00 | `DIM0`–`DIM5` | **6 个通道亮度全部清零（全灭）** |

后续还有一批（`0x402079c1` 之后）：`0x20`–`0x24`、`0x14`(`EN_BRE` 呼吸使能)、
`0x11`(`CTL`)、`0x05`(`GPIO_CFG_B`)、`0x17`–`0x19`(`DLY0_BRE`–`DLY2_BRE`)、
`0x15`(`FADE_TMR`)、`0x16`(`FULL_TMR`) —— 是一套**呼吸灯/渐亮渐灭**配置。

寄存器名与地址均与 AW9106 规格书一致，说明固件里这颗驱动就是**给 PCB 上那颗 AW9106BTQR 用的**。

## 4. 6 个通道各自有独立的 setter

`DIM0..DIM5`（0x20..0x25）对应 6 路恒流输出，固件里一个通道一个函数：

| 函数 | 写寄存器 |
| --- | --- |
| `0x402079b0` | 0x20 (`DIM0`) |
| `0x402079c8` | 0x21 (`DIM1`) |
| `0x402079e0` | 0x22 (`DIM2`) |
| `0x402079f8` | 0x23 (`DIM3`) |
| … | 0x24 / 0x25 (`DIM4`/`DIM5`) |

6 路可以驱动 6 颗单色 LED，或 2 颗 RGB 灯珠（规格书典型用法）。

## 5. 同一条 I2C 上还有一颗芯片：0x19 = SC7A20 加速度计（已确认）

分析时我在 `0x4012388b` 一带发现另一段 I2C 代码，用的是地址 **0x19**，写寄存器：

- `0x20 0x21 0x22 0x23 0x24 0x25`
- `0x30 0x31 0x32`，并**读 `0x31`**

我一开始误以为是第二个 LED 驱动，对照寄存器表后确定这是**三轴加速度计**：

| 寄存器 | 含义 |
| --- | --- |
| 0x20–0x25 | `CTRL_REG1`–`CTRL_REG6` |
| 0x30 / 0x31 / 0x32 | `INT1_CFG` / `INT1_SRC` / `INT1_THS` |

### 决定性证据：固件会校验 WHO_AM_I

函数 `0x40123918` 一开始就做身份检查：

```
40123921: movi.n a11, 15      ; 寄存器 0x0F = WHO_AM_I
40123923: movi a10, 25        ; 从机地址 0x19
4012392c: call  read_helper   ; 读回 1 字节
40123932: movi.n a8, 17       ; ★ 期望值 = 17 = 0x11 ★
40123934: l8ui a9, a1, 0      ; WHO_AM_I 的返回值
4012393a: beq a9, a8, ...     ; 相等才继续初始化
4012393d: j 0x401239f8        ; 不等 → 直接走错误/退出
```

**这颗芯片必须在 `WHO_AM_I`(0x0F) 返回 `0x11`，否则驱动拒绝工作。**

- LIS3DH / LIS2DH / LIS2DH12 的 WHO_AM_I 是 **0x33**
- **SC7A20（士兰微 Silan）的 WHO_AM_I 是 `0x11`**

因为这是**量产固件**（设备能正常工作），板上焊的芯片必然返回 0x11 ——
所以它**不可能是 LIS3DH**，而是 **SC7A20 这一类**（SC7A20 是 LIS2DH/LIS3DH 的寄存器兼容克隆，
Linux 内核有专门的 `st_accel` 补丁支持它）。

地址 0x19 还说明 **SA0/AD0 地址脚被拉高**（若拉低则是 0x18）。

### 固件写入的初始化值（可对照规格书核）

| 寄存器 | 值 | 说明 |
| --- | --- | --- |
| 0x21 `CTRL_REG2` | 0x91 | 高通滤波配置 |
| 0x22 `CTRL_REG3` | 0x40 | 把 AOI1 中断路由到 INT1 引脚 |
| 0x23 `CTRL_REG4` | 0x88 | BDU=1、量程 ±2g、高分辨率 |
| 0x24 `CTRL_REG5` | 0x80 | |
| 0x30 `INT1_CFG` | 0x2A | AOI 组合条件 |
| 0x32 `INT1_THS` | 0x65 | 中断阈值 |
| 0x20 `CTRL_REG1` | 0x41 | 最终写入（ODR/轴使能） |

中断由 GPIO ISR 喂给一个名为 **`gsensor_block`** 的任务处理
（同批任务还有 `gpioclear` / `gpiopress` / `gpiolongpress`）。
INT1 具体接哪根 ESP32 GPIO 我还没定位到（注册调用落在反汇编失步区），
可以用逻辑分析仪或万用表沿 INT1 追。

### 一分钟终极验证

在这条 I2C 上读一次地址 0x19 的寄存器 0x0F：

- 返回 **0x11** → SC7A20（和固件要求一致，确认）
- 返回 0x33 → 那才是 LIS3DH（但量产固件不会接受它，说明有问题）

顺便量一下 **SA0/AD0 脚应为高电平**（对应 0x19）。

## 6. 这对之前的 GPIO 结论意味着什么

- **主板上的 LED 走这颗 I2C 芯片，不占 ESP32 的 GPIO** —— 这解释了为什么我先前扫不出「LED 的 GPIO 引脚」。
- 头部/尾部 LED 仍然在**底座板**上（走 UART 的 `{AT+HLY}` 等命令），两者不冲突：
  AW9106 驱动的应该是主板自己的指示灯/氛围灯。
- 现在 ESP32 的引脚账基本完整了：

| 外设 | 引脚 |
| --- | --- |
| SPI LCD（160×128，10 MHz） | SCLK 32 / MOSI 33 / MISO 34 / CS 27 / DC 21 / RST 22 |
| TF 卡（SDMMC slot 1） | CLK 14 / CMD 15 / D0 2 / D1 4 / D2 12 / D3 13 |
| **I2C0（AW9106 @0x5B + G-sensor @0x19）** | **SDA 18 / SCL 23** |
| 某芯片复位线 | GPIO19（输出 + 10 ms 低脉冲） |
| 语音 DSP 控制口 | 第二条 SPI，400 kHz（引脚由运行时结构体传入，未取到） |

## 7. 建议的实测验证（按性价比排序）

1. **万用表通断档**：AW9106 的 SDA/SCL 脚 ↔ ESP32 的 **GPIO18 / GPIO23**。
   对上了，这份分析就闭环了，后面的结论都可以放心用。
2. **量地址脚 AD0/AD1 电平**：都应为高（对应 0x5B）。
3. **逻辑分析仪挂在 SDA/SCL 上开机**：会看到地址 `0xB6` 的一串写操作，
   顺序应该是 `7F←00, 11←10, 12←02, 04←00, 02←00, 13←00, 20..25←00 …`
   —— 与本文第 3 节逐字节对得上，那就是铁证。
4. **找 SHDN 脚**：AW9106 的 SHDN 低有效，正常工作时必须为高。顺便量一下
   **GPIO19 是不是接到了某颗芯片的 SHDN/RESET**（固件里 GPIO19 是「拉低 10 ms 再拉高」的复位脉冲，
   时序与复位脚完全吻合）。
5. 确定 6 路输出（OUT0–OUT5）分别接哪颗 LED —— 这部分只能靠 PCB 走线追。

---

## 8. 一句话总结

**AW9106BTQR 挂在 I2C0 上：SDA = GPIO18，SCL = GPIO23，100 kHz，7 位地址 0x5B
（写 0xB6 / 读 0xB7）；固件里 tag 为 `aw9106` 的驱动（`chip_aw9110b_init` @ 0x402078dc）
按规格书寄存器表（0x7F 复位、0x11 CTL、0x20–0x25 六路 DIM）把它初始化成呼吸灯模式。
同一条总线上还有一颗 0x19 的加速度计（G-sensor），不是 LED。**
