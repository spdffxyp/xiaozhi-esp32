# LED 指示灯与底座通信：实现说明与待上机确认项

对照对象：[FlowerCat-chen/Flower_modou](https://github.com/FlowerCat-chen/Flower_modou)（`ref/Flower_modou/`），
同硬件开源适配工程。本轮按它补齐了两块之前完全没有的东西：**板载指示灯**和**底座（电机/头尾灯）通信**。

> 本轮**没有真机调试**（电脑未接开发板）。下面每条都标了"已核对什么 / 还需要上机确认什么"。

## 1. 指示灯（AW9106B 0x5B）—— 新增 `b220_led.c/h`

### 1.1 这个芯片上到底挂了几路什么

| 寄存器 | 本机（B220） | Flower_modou 的机器 |
| --- | --- | --- |
| `0x20` `0x21` `0x22` | **LCD 背光**（`InitializeBacklight()` 写 `0x3F`；实测"六路走查时屏亮"就是这三路） | 顶部 RGB 灯（G/R/B） |
| `0x23` `0x24` | 指示灯（工厂回放留在 `0x80`，之前**从来没有代码再碰过**） | 同两路（`0x23/0x24 ← 0x80`） |
| `0x25` | 本移植未用 | 初始化时清 0 |

> ⚠️ **关键差异**：参考项目把 `0x20/0x21/0x22` 当 RGB 灯，而在本机上这三路是背光
> （把 `0x3F` 写进去屏才亮）。所以**不能照抄它的颜色映射**，否则会把背光当成彩灯拉来拉去。
> 本轮的处理：`b220_led.c` **只驱动 `0x23/0x24`**，背光三路只提供"调亮度"接口、绝不参与灯效。

#### ❌ 上机实测发现：`0x23`/`0x24` **不能拉到 0x80 以下**（会关屏）

第一版 `b220_led.c` 把 `0x23/0x24` 当普通指示灯：待机写 `0x00`、按键时闪 `0x30 → 0x00`。
上机现象：**一按按键屏幕闪一下、随后黑屏**。原因就是这两路里有**至少一路接的是 LCD 的
电源/背光**（参考项目自己的备注也写着 `0x23/0x24 相关 LCD power/backlight 控制`），
把它拉到 `0x80` 以下屏就黑了。

**已改为**：`0x23/0x24` 的**下限锁死在 `0x80`**（= 工厂回放后屏正常工作时它们本来就有的值），
灯效只能在这个基线之上变化，绝不写更低的值；开机也不再"待机熄灭"。

**上机待办（重要）**：`0x23`/`0x24` 到底是"LCD 电源"还是"指示灯"，以及本机是否**根本没有**
可安全驱动的独立指示灯 —— 需要逐路点灯走查确认。在确认之前，灯效的可见效果可能不明显
（因为下限被锁住），但**不会再关屏**。

### 1.2 已实现

- `b220_led_start()`：在板级已建好的 I2C0 上挂一个**自己的** 0x5B 设备句柄（不创建/不释放总线，
  与板级的设备句柄互不干扰），把指示灯设为**待机熄灭**（参考实现的省电选择），并起一个 20 ms 的
  灯效任务。
- `b220_led_blink_once()`：两下短闪（`0x30`，60 ms 亮 / 70 ms 灭）。**非阻塞**，所以从按键回调里调是安全的。
- `b220_led_set_indicator()/set_both()/set_backlight()/get_backlight()/get_state()`。
- 按键动作会闪一下灯（`B220_ButtonAction()` 里）—— 这是这块玩具在没有屏幕时的唯一反馈。

### 1.3 安全边界（必须守住）

AW8737S 的 SHDN 是 `reg 0x02` 的 bit1，**靠上升沿计数选模式，一个 boot 只允许一个沿**（PART 2 §9）。
所以 `b220_led.c` **只写 `0x20..0x25`**，永不触碰 `0x02/0x04/0x12`（那三个由板级的 PA 使能独占并锁存）。
代码里有注释明写这条，改动前请先读 `b220_led.h` 的头注释。

### 1.4 还需要上机确认

| 待确认 | 怎么确认 |
| --- | --- |
| **`0x23`/`0x24` 是不是 LCD 电源/背光**（已实测"写到 0x00 会关屏"） | 用 `b220_led_set_indicator()` 逐路从 `0x80` 往下试（**会关屏，但重启即恢复**），或直接量屏供电/背光脚的通断 |
| `0x23`/`0x24` 各自对应哪颗实体灯 | 上机后 `b220_led_set_indicator(A, 0x3F)` / `(B, 0x3F)` 单独点，肉眼记录 |
| 本机是否也有"顶部 RGB"（挂在别的通道或别的芯片） | 参考项目说顶部 RGB 是 `0x20/0x21/0x22`，但本机那三路是背光 ⇒ 本机的顶部灯要么不存在，要么在别处。需要点灯走查一遍全部 6 路 |
| 待机熄灭是否合适 | 现在 `s_indicator_idle = 0x00`（参考实现同款省电策略）。若希望待机指示可视，改 `b220_led.h` 的 idle 值 |
| 亮度上限 | 跟参考实现一致用 `0x3F`（= `MODOU_KEY_LIGHTS_MAX_BRIGHTNESS`） |

### 1.5 有意**没有**照抄的部分：AW9106 初始化序列

参考项目的 `apply_factory_aw9106_led_init()`：

```
7F←00, 11←10, 12←02, 04←00, 02←00, 13←00,
20←00, 21←00, 22←00, 24←00, 24←00, 25←00,
14←07, 05←07, 17←01, 18←01, 19←01,
15←1B, 16←08,
23←80, 24←80,
02←02,          <-- 功放使能（唯一上升沿）
14←00, 11←12    <-- 使能之后的两条
```

与我们的 `InitializeBacklight()` 对比，**差异只有三处**：

| 差异 | 我们的值 | 参考值 | 是否照抄 |
| --- | --- | --- | --- |
| `0x15` | 不写 | `0x1B` | ❌ 本轮不抄（见下） |
| `0x16` | 不写 | `0x08` | ❌ 本轮不抄 |
| 末尾 | 停在 `0x11 ← 0x1B` | `0x14←00, 11←12` | ❌ 本轮不抄 |

**为什么不抄**：`0x11`/`0x14` 落在那组 **0x1B/0x12 的模数校准寄存器**里（0x11–0x19），
而我们的背光是靠 `0x11 ← 0x1B` + `0x12 ← 0x02` 这个组合亮起来的（实测确认）。
参考机的背光在别的通道，两者的校准点**不保证相同** —— 在不能上机验证的情况下改这三条，
风险是"屏不亮"或"背光亮度变化"，收益却只是"和参考项目更像"。所以本轮**只记录、不改**。

想试的话，改动点很集中：`xiaomodou_b220.cc` 的 `InitializeBacklight()` 的 `init_seq` 末尾加
`{0x15,0x1B},{0x16,0x08}`，并在 PA 使能之后补 `0x14←0x00, 0x11←0x12`。
**回滚方式**：删掉这三条即可（当前版本就是基线）。

## 2. 底座通信（UART0）—— 新增 `b220_base_uart.c/h`

### 2.1 总线与协议（已核对）

| 项 | 值 | 依据 |
| --- | --- | --- |
| 端口 / 引脚 | **UART0，TX GPIO1 / RX GPIO3** | 与移植手册一致；Flower_modou `modou_base_uart.c` 同 |
| 参数 | 115200 8N1 | 同 |
| 帧格式 | `{AT+...}\r\n`（大括号 + CRLF） | Flower_modou `modou_base_uart.c: snprintf(frame, "{%s}\r\n", cmd)`，其底座测试页在真机可用 |
| 已知可用命令 | `AT+Ver`（有回包）、`AT+Pon`（唤醒并解锁电机）、`AT+Onbase`、`AT+Run`、`AT+CMD=(...)` | 同上 |

### 2.2 ⚠️ 与日志/烧录口共用一根线（这是最大的坑）

GPIO1/3 同时是**控制台日志**和**烧录口**。参考实现自己也在源码里注明"日志可能会和底座协议
混在同一物理线上，所以只做诊断探测"。两个方向的后果：

- 我们发出的 `{AT+...}` 也会出现在串口日志里（**看到是正常的，不代表有问题**）；
- 我们打印的日志也会进底座，底座对不认识的文本忽略处理（原厂固件就是这么共存的）；
- 底座的回包会进控制台输入，可能被 IDF 控制台打印成"unknown command"之类的噪声。

另外注意：**烧录时不要指望底座那侧安静** —— 用 `flash-b220.ps1` 刷机和抓日志都走同一根线。

### 2.3 已实现

- `b220_base_uart_init(bool consume_console_input)`：默认**只发不收**（`false`），不动控制台的输入；
  需要读回包时显式传 `true`（会接管 RX 缓冲）。
- `b220_base_uart_send(cmd, tx_timeout_ms)`：加 `{}` + CRLF 后发送，带互斥锁，非阻塞（只等 FIFO 排空）。
- `b220_base_uart_send_and_receive()` / `b220_base_uart_read_pending()`：读回包（读到 `\n` 为止）。
- **开机握手**：`B220_BASE_UART_HANDSHAKE = 1` 时，延迟
  `B220_BASE_UART_HANDSHAKE_DELAY_MS = 3000` ms（让 ROM 横幅和开机日志先吐完）后发一次 `AT+Pon`
  —— 这是解锁电机的关键一步（参考实现："`AT+Pon` 成功发送一次后即可解锁电机"）。
- 运动/灯光封装：
  - `b220_base_motion(mode, steer, power, duration_ms)` → `AT+CMD=(9,1,0,1),(mode,units,steer,power,0),(0,0,0,0)×4`
    （`units` 按 **200 ms 向上取整**，`steer` 钳 0..180、中点 90，`power` 钳 1..100，`power=0` 等价于停止）
  - `b220_base_stop()` → 两条停止帧（逐字取自参考项目的 `BASE_STOP_CMDS`）
  - `b220_base_lights(front, rear)` → 头/尾灯帧

运动模式语义（参考项目 `docs/MOTOR_REMOTE_PROTOCOL_2026-07-30.md`）：`0/1` 原地左右转，
`2/3` 后退/前进（左半区），`4/5` 后退右弯/前进右弯；`81..99` 归一化为 `90` 直行。

### 2.4 还需要上机确认

| 待确认 | 说明 |
| --- | --- |
| **`AT+Pon` 一发出去就报错**（已实测） | 上机日志：`E uart: uart_write_bytes(1705): uart driver error` + `write short (-1 of 10 bytes)`。原因：**控制台占用了 UART0**，`uart_write_bytes` 那条路径没有可用的 TX 缓冲。下面的 §2.5 是修法 |
| 底座是否有回包 | 需要 `b220_base_uart_send_and_receive()`（即 `init(true)`）。**先不加**到默认路径，避免抢控制台输入 |
| `AT+Pon` 之后电机是否真的解锁 | 上机时看底座是否开始回 `{AT+OK}` 之类，并试一条 `b220_base_motion(3, 90, 40, 600)` |
| 模式 0/1 与左右方向是否要互换 | 依赖装配朝向，必须实机看 |
| 头/尾灯的"颜色索引" | 参考项目用 `7,<色号>,2000,<目标1/2>`；色号 0=白 1=红 … 7=紫。我们的 `b220_base_lights()` 只做"白/红 + 目标 1/2"，其余等实测 |
| 与烧录/日志的相互干扰程度 | 上机抓一次 `AT+Pon` 前后的完整串口日志即可看清 |

### 2.4b 日志走 TCP：把 UART0 让给底座（2026-10-11）

### 为什么需要它

底座挂在 **UART0** —— 和烧录/控制台**同一根线**。底座一插上就**物理挡住那个接口**，
于是最需要调试底座的时候，串口日志反而读不到；而且只要控制台占着这个口，
**底座的回复也读不到**（`AT+Ver` 等查询要回复）。

用户的想法是"日志走网络"。**这一下把之前 A/B/C 的三难解开了**：

| | 之前 | 现在 |
| --- | --- | --- |
| 日志 | 只有 UART0 | **WiFi/TCP** |
| 底座 TX | 方案 B 可行 | 完整 |
| 底座 **RX**（读回复） | 控制台占用，**读不到** | **可读**（UART0 归我们后） |
| 物理接线 | 底座一插就挡 | **不再需要** |

### 为什么不是"控制台自带的功能"

IDF 6.1 **没有**现成的网络日志传输层（只有 `esp_log_set_vprintf()` 这个钩子），
所以是自己实现的。这有个额外好处：**钩子能在 `app_main` 之前装上**。

### 实现（`b220_tcp_log.cc/.h`）

- **钩子时机**：用 **C++ 静态初始化**（`kTcpLogInstalled = (TcpLog::instance().start(), 0)`），
  在任何代码运行前执行 ⇒ **从板级构造函数的第一条日志起**全部进缓冲。
  已用符号+反汇编验证：`_GLOBAL__sub_I_b220_tcp_log_start` 在构造表里，且其函数体
  `call8 TcpLog::start()`；
- `esp_log_set_vprintf()` 钩住所有日志 → 写入**8 KB 环形缓冲** → **同时仍然调用原来的
  handler**，所以**串口日志行为完全不变**（这一步零风险）；
- **TCP 监听 :3333**（`nc <IP> 3333`），最多 4 个客户端；
- **新客户端会收到缓冲区内全部历史** ⇒ 即使 WiFi 要 8 秒才起来，**启动日志不会丢**；
- 每个客户端有独立读位置，跟不上时被前推（丢旧行，而不是收到撕裂的行）；
- **发送只在监听任务里做**，钩子内不做任何 I/O ⇒ 慢客户端/死客户端**不可能拖住系统**；
- 实测占用：`TcpLog::instance` = **8248 字节**（8192 环形 + 56 状态），
  任务栈 4 KB 来自堆；空闲 SRAM 约 94 KB，够用。

### 兜底：网络起不来怎么办

"网络起不来"本身就是要排查的故障之一，而它会让日志通道一起消失。所以：

**按音量−键** ⇒ 把最近日志从**串口**吐出来。用一个已经有别的职责的键，是**故意**的：
调试手段不能依赖于被调试的东西。开关 `B220_TCP_LOG_DUMP_ON_VOLUME_DOWN`（默认 1）。

### ★ 上机第一次就崩了：静态初始化里不能碰 lwIP

第一版把"创建并 bind 监听 socket"也放在静态初始化里（和钩子一起），上机立即：

```
assert failed: tcpip_send_msg_wait_sem /components/lwip/lwip/src/api/tcpip.c:454 (Invalid mbox)
```

**根因**：板级构造函数在 `Application::Initialize()` 第 62 行就被触发（`Board::GetInstance()`），
而 **`board.StartNetwork()` 在第 170 行** —— 也就是说**静态初始化时 lwIP 的 mbox 还不存在**，
建 socket 必然断言失败。

**修法：把"装钩子"和"开 socket"分开**

| 部分 | 何时运行 | 为什么 |
| --- | --- | --- |
| 钩子 + 环形缓冲 | **静态初始化**（最早） | 只用到 RAM；**必须最早**才能抓到启动日志 |
| 监听 socket | **TCP 任务里**，先 `wait_for_network()` 轮询默认 netif 出现 | socket 属于 lwIP；任务上下文也本就适合阻塞式 bind/accept |

反汇编验证（`task_entry` 内联了 `run()`）：
```
l32r a8, <esp_netif_get_handle_from_ifkey> ; callx8   <- 先等网络栈
l32r a8, <vTaskDelay>                      ; callx8   <- 等待/重试
l32r a8, <lwip_socket>                     ; callx8   <- 之后才建 socket
l32r a8, <vTaskDelete>                     ; callx8   <- 等不到就优雅降级，不崩
```

**教训（同一类错误的又一次）**：我上一轮验证了"静态初始化确实调用了 `start()`"，
但**没有验证"在那个时刻运行是否安全"**。机制被证明了，**前提没有被证明**。

> **静态构造函数里不能碰任何子系统**（网络、文件系统、驱动、NVS）—— 那时它们都还没初始化。
> 静态初始化只适合做"纯内存"的准备（装钩子、备缓冲），凡是需要子系统的动作都要延后到任务里、
> 并**显式等待**那个子系统就绪，而不是假设初始化顺序。这个项目已经因为"假设顺序"错过多次
> （编解码器启动、灯光策略、这次的 lwIP），所以正确做法是**轮询到就绪**而不是依赖执行次序。

### 第 2 步：UART0 完全归底座（已实现，待上机）

配置：`config.json` 加 `CONFIG_ESP_CONSOLE_NONE=y` ⇒ 生成结果

```
# CONFIG_ESP_CONSOLE_UART_DEFAULT is not set
CONFIG_ESP_CONSOLE_NONE=y
CONFIG_ESP_CONSOLE_UART_NUM=-1        <- 控制台不再占 UART0
```

代码（`b220_base_uart.c`）**同一份源码兼容两种情况**，并在启动日志里明说走了哪条：

| 构建 | 谁拥有 UART0 | TX | RX |
| --- | --- | --- | --- |
| console 开（默认构建） | 控制台驱动（TX 环=0） | ROM 发送器 | 只有控制台的输入环，实际**只发不收** |
| **console 关（底座构建）** | **我们**（`uart_driver_install(0,512,256,...)` 成功） | 驱动 | **可读** —— 这是关掉 console 的**全部意义** |

反汇编确认 init 的调用次序：`uart_param_config → uart_set_pin → uart_is_driver_installed
→ uart_driver_install`。

### ★ 没有底座也能验证 UART 通路：片内回环自检

底座没接时，"底座没回应"和"UART 根本没通"长得一模一样 —— 而后者正是**错的 console 设置或错的引脚**会造成的。
所以加了 `b220_base_uart_selftest()`：用 `uart_set_loop_back()` **在芯片内部短接 TX/RX**，
发一帧、读回来比对。它一次性验证驱动、收发环、时钟分频和引脚复用。

- 开关 `B220_BASE_UART_SELFTEST`（默认 **0**）：它会往线上发字节，真底座可能当成命令，所以只在
  排查时打开、看一次启动、再关掉；
- 在"控制台拥有端口"的构建里它直接报 `ESP_ERR_INVALID_STATE`（读不到回环），这本身就是有用的信息。

### 另外：底座回复以前**从来没被打印过**

`b220_base_uart_read_pending()` 在正常运行时**没有任何调用者** —— 于是"底座没回"和"我们没看"
无法区分。新增 `b220_base_uart_start_rx_report()`（开关 `B220_BASE_UART_RX_REPORT`，默认 **1**）：
把底座发来的一切打出来（`baseboard says: ...`）。这样第一次上机就能确定**到底有没有回包**。

### 上机结果（2026-10-11，telnet 读到）

**第二步成功**，三条证据：

```
I (5577) b220-base: baseboard link up: UART0 TX GPIO1 / RX GPIO3 @ 115200 8N1,
                    THIS module owns the driver (the console is off), so frames go out
                    through it and replies are readable
I (8577) b220-base: baseboard handshake: sending AT+Pon (this is what unlocks the motors)
I (8577) b220-base: baseboard handshake sent
```

- **`THIS module owns the driver`** ⇒ `uart_driver_install` 成功（第 1 步那版是装不上的）；
- **`handshake sent`** ⇒ `AT+Pon` **真的发出去了**。之前是
  `uart_write_bytes: uart driver error` + `write short (-1 of 10 bytes)`；
- 而且**这段日志本身是从 telnet 读到的** ⇒ TCP 已然成为主通道。

顺带一个提醒：`I (5577) uart: ESP_INTR_FLAG_IRAM flag not set while CONFIG_UART_ISR_IN_IRAM is
enabled, flag updated` —— 这条**不是错误**（驱动自己修好了），但它是噪声，会让人怀疑 install
是不是失败了。已改为显式传 `ESP_INTR_FLAG_IRAM`。

### 长行截断：改法换了一次，因为第一版是错的

上机时看到 259 字节那行末尾出现 `...[cut]`。实测本固件**只有 4 行超过 256 字节**
（全场 234 行），最长 **466 字节**，而它被截掉的尾部恰恰是
`per step: 1/5 upload=done … 5/5 soft reset=ok` —— **DSP 启动的逐项结论**。

我第一版的修法是"把长行拆成多条环形条目"，**写完就发现是错的**：
`vsnprintf` **没有"从偏移继续"的形式**，要拆就必须每块都从**头**重新格式化并丢弃前缀 ——
这既不符合 `va_list` 的语义（用一次即失效），机制也远比问题本身复杂。**已废弃**。

**采用的修法**：缓冲 **256 → 512**（覆盖本固件所有行，最长 466），并且**为它付账**——
把 `CONFIG_ESP_SYSTEM_EVENT_TASK_STACK_SIZE` 从 2304 提到 **3584**（约 1.3 KB 堆）。
理由很直接：**用 1.3 KB 堆换掉一个"能打崩设备"的故障**是划算的，而用一个会丢关键诊断的
小缓冲去省它，不划算。`...[cut]` 标记保留为**兜底**（正常启动下不该再出现）。

### ⚠️ 第 2 步的代价：串口兜底失效

第 1 步那个"按音量−从串口吐日志"的兜底，在 console 关闭的构建里**很可能不再有输出**
（`CONFIG_ESP_CONSOLE_NONE` 会让控制台在启动时不被初始化）。**本步骤尚未上机，
所以这一条我标注为"很可能"而不是断言** —— 上机时按音量−观察串口是否有反应即可确认。

含义要说清楚：**底座构建里 TCP 是唯一的日志通道**。这和现实一致（底座一插就挡住接口，
本来也没有第二条线），但意味着**UART0 一旦配错就没有本地输出**，只能切回 console 版重刷。

### 分两步走（第 1 步已完成，第 2 步待上机）

| 步骤 | 内容 | 状态 |
| --- | --- | --- |
| **第 1 步** | 只加 TCP 日志，**串口不动** | ✅ 已实现，待上机 |
| 第 2 步 | `CONFIG_ESP_CONSOLE_NONE` + UART0 装我们自己的驱动（`install(0, 512, 256, ...)`）+ **收发双向** | 待第 1 步验证后做 |

**第 2 步的代价必须说清**：`CONFIG_ESP_CONSOLE_NONE` 会让**最早期输出消失** ——
包括 **bootloader 的 `rst:0x…` / `flash read err`**，以及 IDF 启动的 `app_init:`
（含 **`Compile time` / ELF SHA**）。而我们正是靠 `Compile time` 发现过"刷的不是最新固件"。
所以第 2 步会做成**编译开关**：平时用网络日志+完整 UART0，需要看启动早期问题就切回串口版。

## 2.5 上机实测：`AT+Pon` 发不出去（`uart driver error`）—— 原因与修法

```
I (13994) b220-base: baseboard handshake: sending AT+Pon (this is what unlocks the motors)
E (13994) uart: uart_write_bytes(1705): uart driver error
W (13994) b220-base: baseboard write short (-1 of 10 bytes)
```

`uart_write_bytes()` 返回 −1 并打 `uart driver error`，只有一个含义：**这个 UART 的 TX
环形缓冲不可用**。本机 UART0 被 **ESP-IDF 控制台（`CONFIG_ESP_CONSOLE_UART_DEFAULT`）独占**——
控制台走的是 ROM 的 `ets_printf` 直写路径，并没有为 `uart_write_bytes()` 准备 TX buffer，
所以这个调用必然失败。参考项目之所以能发，是因为它的工程把控制台关掉了
（`CONFIG_ESP_CONSOLE_NONE` / USB-Serial-JTAG），两者不能同时成立。

三条可选路（按推荐顺序）：

1. **把控制台让给底座（推荐）** —— `sdkconfig` 里改
   `CONFIG_ESP_CONSOLE_UART_DEFAULT=n`，改用 `CONFIG_ESP_CONSOLE_NONE=y`
   （或若硬件支持则 `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y`）。这样 `uart_write_bytes()`
   可用，代价是**串口日志没了**。因为本机刷机/日志都靠 UART0，建议只在"专门验证底座"的构建里这么做。
   > 注意 `flash-b220.ps1` 靠 `--after watchdog_reset` 复位，不依赖控制台，所以关掉控制台不影响刷机。
2. **不装驱动，直接用 ROM 的写接口** —— 用 `esp_rom_printf()` / `ets_printf()` 发帧。
   它绕过 `uart_write_bytes()`，在控制台启用时也能出去（日志本来就靠它）。
   代价：阻塞式、没有互斥、而且**会和日志混在同一条流上**（底座要能容忍前面那串日志）。
3. **换到别的 UART** —— 本机**没有**第二组空闲脚可用（GPIO16/17 是 PSRAM，其余都被 LCD/I2S/HBI/I2C 占了），
   所以这条路不成立；除非愿意牺牲某个外设。

**本轮的处置**：默认路径保持"发不出去就明确报错"（不静默），并在下面 §4 的待办里列出
"是否改成方案 1/2"。这样上机时一眼能看到是"没通电"还是"控制台占着"。

## 2.6 按键长按：**结论是硬件做不到**（三次尝试、带仪器化实测）

### 最终结论（有测量数据，不是推理）

用带仪器化的固件跑了一轮"短按 / 长按"对照，窗口每次关闭都打印"活了多久 + 为什么关 +
这期间 status 读到了什么"：

| 操作 | 窗口关闭原因 | 寿命 | status 读取统计 | GPIO38 |
| --- | --- | --- | --- | --- |
| 短按 VOL− | `no signal for the whole gap window` | 198 ms | **1 press, 15 idle** | 高 |
| 短按 VOL− | `release event (status 0x0002)` | 142 ms | 1 press, 10 idle | 高 |
| 短按 VOL+ | `release event (status 0x0002)` | 184 ms | 1 press, 14 idle | 高 |
| **长按 VOL−（4 s）** | `no signal ...` | 197 ms | **1 press, 15 idle** | 高 |
| **长按 VOL+（4 s）** | `no signal ...` | 197 ms | **1 press, 15 idle** | 高 |

⇒ **长按 4 秒和短按 0.3 秒产生的序列逐条相同**。于是可以断定：

1. **一次物理按压只报一个 `0x0003`**（带按键码），此后不再有任何事件；
2. **按住时长不可读**：`status` 在按下后立刻回到 `0x0000`；
3. **`0x0002` 不是"手指松开"**：它在按下后 140~200 ms 出现，**与真实按住时长无关**，
   更像是"这个事件已被主机消费"的应答；
4. **GPIO38 不是"按住"信号**：按住全程读作**高**（它在启动瞬间读 0 是上电残留）。

### 三次失败的经历（全部保留，避免第四次）

| 版本 | 做法 | 结果 |
| --- | --- | --- |
| v1 | `key != 0x8400` 当"按着" | 把事件当电平，`held 9 ms` |
| v2 | 用"事件间隔"维持窗口 | 前端在按住期间**不发重复事件**，窗口自灭 |
| v3 | 用 **GPIO38 低电平**当"还按着" | 该线**不跟随按键**（本次已量到：按住时读高） |
| v4 | 每 10 ms 轮询状态寄存器 | 状态**不保持**（1 press + 15 idle） ⇒ 同样不可读 |
| **定稿** | **不做长按** | 每个键一次按下 = 一次动作 |

> 过程中的两次自我纠错也记一笔：我曾根据一份日志断言"一次按压会产生两个 `0x0003`"，
> 那是**误读**（把两次不同的按键当成一次）；后来加了"窗口开启/关闭都必有日志"才发现
> 真正的问题是窗口静默关闭 —— **日志设计不当会让两种完全不同的故障长得一模一样**。

### 代码现状

- `b220_buttons.h/.c`：删掉长按判定、hold 窗口、GPIO38 电平推断与所有相关日志
  （净减代码，也没有了误导性的 `held 0 ms`）；
- 回调签名简化为 `void (b220_button_action_t)` —— 不再有永远为 `short` 的时长参数；
- 每个键：**一次按下 = 一次动作**（音量 ±`B220_BUTTON_VOLUME_STEP`）；
- `B220_BUTTON_LONGPRESS_MS` 已从 `config.h` 删除（不再有人用）。

### 如果将来还想要"音量直接到顶"

唯一诚实的做法**不是长按**，而是：

- **连按**：快速按两下 → 直接到 100 / 0（需要实现一个双击窗口，约 400 ms，可靠）；
- 或者在本地 UI / 云端用一个语音指令。

## 2.6 按键长按：两次上机失败后的最终模型（`b220_buttons.c`）

### 失败经历（都记下来，避免第三次）

| 版本 | 做法 | 上机结果 | 为什么错 |
| --- | --- | --- | --- |
| v1 | 把 `0x0002 != 0x8400` 当"按着" | `held 9 ms`，长按无效 | 把事件当电平 |
| v2 | 用"事件间隔"维持按住窗口 | `held 0 ms`，长按无效 | 前端在按住期间**不发重复事件**，窗口在 150 ms 后自己关掉 |
| v3 | 用 **GPIO38 低电平**当"还按着" | 仍无 `holding key` 行，长按无效 | 这条线**开机就是低、且不跟随按键**（板级实测），永远给不出"松开" |
| **v4（当前）** | **每 10 ms 轮询状态寄存器**，`0x0003` 即"还按着" | 待上机 | 这才是"物理按住"的真正信号 |

### v3 失败的两个具体 bug（你的日志直接指向它们）

```
W (6024) b220-btn: GPIO38 is LOW at start-up: ...        <- 这条线不可信
W (10664) b220-btn: key VOLUME_UP (short press, held 0 ms): status=0x0003 key=0x0008
（此后 3 分钟没有任何 holding key 行；期间你按住过按键）
```

1. **把 GPIO38 当成"还按着"的唯一依据** —— 它开机为低且不跟随按键，所以 `s_hold_last_us`
   永远得不到刷新，窗口在 `B220_BUTTON_HOLD_GAP_MS` 后关掉；
2. **只在状态寄存器"发生变化"时才读它**，而且读到空闲就把按住窗口清掉 ——
   按下的下一个 poll 只要读到一次 `0x0000`，窗口就没了（约 10 ms，正是日志里的 `held 0 ms`）。

### v4 的模型

```
每 10 ms（或 GPIO38 下降沿）：读 status = HBI 0x0000
  status != 上次 且 status & 1  -> 按下：读 key，执行一次；打开/刷新按住窗口
  status != 上次 且 status==2   -> 抬起：关闭按住窗口（不执行动作）
  status == 0x0003（仍为按下）  -> 算"还按着"，刷新 s_hold_last_us   <-- v4 的关键
"还按着" = (status 当前仍读 0x0003) OR (GPIO38 为低)
两者都不成立满 B220_BUTTON_HOLD_GAP_MS（150 ms）-> 判定松开
按住满 B220_BUTTON_LONGPRESS_MS（2000 ms）-> 触发一次长按（每按一次只报一次）
```

**空闲读数不再清窗口** —— 这条是 v3 的第二个 bug 的修法：一次孤立的 `0x0000`
采样不允许打断一次真实按住。

### 上机怎么判断（日志已经把两个候选信号都打出来）

按住时会每 500 ms 打一行：

```
I b220-btn: holding key 0x000B: 1520 ms | status reads 0x0003 (press) | GPIO38 level 0 | last evidence 0 ms ago
```

- 如果**有这行**且最后出现 `LONG press` → 成功；
- 如果**有这行**但一直没到 2000 ms 就消失 → 看消失前那一行的 `status reads`：
  - 变成 `0x0000 (IDLE)` ⇒ 前端在按住期间把状态清回了空闲，那就得改成"以按下事件为准、
    用固定 2 s 计时"（一次性长按，无法区分按住时长），届时按日志调整；
  - 一直是 `0x0003 (press)` 但窗口还是关了 ⇒ 是我这里的 bug，把日志发我；
- 如果**完全没有这行** → 说明 `handle_press()` 根本没把窗口打开，或者按键事件没到，
  这时看有没有 `key ... (short press` 行来区分。

## 2.8 音量：单击步进 / 双击到顶到底，并且**真正改音量**（本轮新增）

### 2.8.1 双击替代长按

长按做不到（§2.6），但**双击是纯序列关系**，而这个接口对序列是可靠的（一次按下 = 一个 `0x0003`，
按住期间不再有事件）。所以：

| 操作 | 行为 |
| --- | --- |
| 单击音量± | 音量 ±`B220_BUTTON_VOLUME_STEP`（默认 10） |
| **双击同一键**（`B220_BUTTON_DOUBLE_CLICK_MS` = 400 ms 内） | 直接到 100 / 0 |
| 单击录音键 | 立即 `ToggleChatState()`（**不延迟**，否则手感很怪） |

代价说明：单击的步进**延迟 400 ms 生效**（等窗口关闭），这样双击才不会"先走一步再跳"。
若不想要这个延迟，就得接受"双击 = 先 +10 再跳到 100"，可以改 `B220_ButtonAction()`。

### 2.8.2 真正改音量：写 DSP 的 0x0238/0x023A

之前 `SetOutputVolume()` 只存 NVS + UI 不生效（PART 3 §1.6 的设计），现在改成**真的写 DSP**：

```
Zl38063AudioCodec::SetOutputVolume(vol)
    -> AudioCodec::SetOutputVolume(vol)        // 仍然存 NVS（重启保留、UI/MCP 可见）
    -> zl38063_dsp_set_volume(vol)
         -> VprocTwolfSetVolume(gain)          // gain = vol - 90 (dB)
         -> HBI 0x0238 <- gain|gain<<8 ; HBI 0x023A <- gain|gain<<8
```

依据（都是既有证据，不是新猜的）：

| 事实 | 来源 |
| --- | --- |
| 原厂播放路径调 `VprocTwolfSetVolume(tblA[vol/10])`，写 `0x238/0x23A` | PART 2 §6.3（逐指令逆向） |
| 编码 `vol 0 -> -90 dB`、`100 -> +10 dB`（DSP 在 +6 dB 饱和） | `zl38063_dsp.c` 的 `ZL38063_VOLUME_ZERO_DB` 与实测 `0x238=0xECEC`（-20 dB） |
| 这两个寄存器**运行期可写** | 原厂自己的音量/路由例程就是运行期写它们 |
| 本移植已有实现且已接进 HBI | `zl38063_dsp_set_volume()`（原本只在诊断里用） |

**新增日志**（成功与失败都明说）：

```
I Zl38063AudioCodec: SetOutputVolume(80): stored AND applied to the DSP (HBI 0x0238/0x023A, gain = vol - 90 dB)
I XiaoMoDouB220: key VOLUME_UP (single press): volume 70 -> 80
I XiaoMoDouB220: key VOLUME_UP (double press): volume 80 -> 100
W Zl38063AudioCodec: SetOutputVolume(80): stored, but the DSP write failed (ESP_ERR_INVALID_STATE) - the speaker level did not change
```

失败（DSP 没起来 / HBI 写失败）**不影响其它功能**：值照样存下来，日志说清"声音没跟着变"。

### 2.8.3 上机怎么验收

1. 单击音量+ → 应听到**声音变大**（同时日志 `stored AND applied to the DSP`）；再单击几次 → 继续变大。
2. **双击音量−** → 直接静音档（vol 0）；**双击音量+** → 到 100。
3. 单击音量+ 后立刻看日志：`key VOLUME_UP (single press): volume X -> Y`，
   如果只看到 `stored, but the DSP write failed` ⇒ 说明 DSP 那侧没起来或 HBI 写被拒，
   把日志发我（那说明 `0x0238` 在运行期被锁，需要换用配置记录里的 `0x0494/0x049A` 那条路）。

> ⚠️ 一个已知的听感注意点：`0x0238` 的**低 8 位是 Gain B、高 8 位是 Gain A**，本实现两半写同一个值
> （与原厂一致）。如果实测发现"两个声道音量不一致"，那是通道增益对不上，需要分别写 A/B 两半，
> 这一条只能靠耳朵/示波器验，日志看不出来。

## 2.9 上机崩溃：HBI 不是线程安全的（已修，2026-10-10）

### 现象

改音量后设备立刻重启，循环反复：

```
W (37862) b220-btn: key VOLUME_DOWN: status(0x0000)=0x0003 key(0x0002)=0x000A
I (38262) AudioCodec: Set output volume to 60
assert failed: spi_device_transmit spi_master.c:1297 (ret_trans == trans_desc)
Backtrace: ... 0x401720d1 0x400f7114 ...
Rebooting...
rst:0xc (SW_CPU_RESET)
```

### 根因：**一条 HBI 命令不是原子的**

`hbi_send_cmd()` 访问 page 0 以外的寄存器要**两个 SPI 事务**（先 `SELECT_PAGE`，再读写），
即使 page 0 也是"命令事务 + 每个数据字一个事务"。而 `zl38063_hbi.c` **没有任何锁**：

- 改音量之前，HBI 的**唯一**使用者是启动任务（boot + 诊断），单线程，所以从来没暴露；
- 加入按键轮询（10 ms 读 `0x0000/0x0002`）后仍只是多了一个读者；
- **这一轮把音量写接到 `SetOutputVolume()`，它从另一个任务（esp_timer / 音频路径）调用 HBI**
  ⇒ 两个任务的事务交错：B 任务的 `SELECT_PAGE` 插进 A 任务的"选页"和"payload"之间，
  A 的数据被写到**错误的页**，SPI 驱动随即以 `ret_trans == trans_desc` 断言中止。

这是**我自己引入的并发缺陷**：新增 HBI 调用者时没有先确认底层是否可重入。

### 修法

在 `zl38063_hbi.c` 里加**递归互斥锁**（`xSemaphoreCreateRecursiveMutex`，惰性创建），
并让**整条命令**处于锁内：

| 函数 | 锁的粒度 |
| --- | --- |
| `zl38063_hbi_read()` / `zl38063_hbi_write()` | **整条命令**：SELECT_PAGE + 命令 + 全部数据字 |
| `zl38063_hbi_wr16_cmd()` / `wr16_data()` / `rd16()` | 单次事务（可被上面的组合调用重入） |
| `zl38063_hbi_set_swap()` | 改全局字节序状态时 |

递归是必须的：`hbi_read()` 会调 `hbi_send_cmd()` → `wr16_cmd()`，同一任务要拿两次锁。
超时用 500 ms：卡死的持锁者不能把调用者拖死。

### 仍然待验

- 修复后需重新刷机确认不再重启（本轮无硬件）；
- 若在**高频连按**音量时仍有异常，说明 500 ms 超时或锁粒度还不够，把日志发我。

## 2.9a-pre-2 两处上机反馈的修正（2026-10-11 第二次）

### ① 待机灯在按音量键后熄灭 —— 策略的"值未变就跳过"

**现象**：idle 时灯微亮，调一次音量后灯灭了。

**根因**：`policy_apply()` 在"模式没变"的分支里，把 `B220_LIGHT_IDLE` 和
`B220_LIGHT_NO_CLOUD` 这两个**常亮模式**落进了 `default: break;` —— 也就是"已经写过，不用再写"。
但按键反馈脉冲（`b220_led.c`）结束时会把灯设成 **`B220_LED_OFF`**，而**之后再没有任何东西把它写回待机色**，
所以灯就一直灭着。呼吸模式不受影响（它们本来每 tick 都写），所以只有"常亮"这一路暴露。

**修法**：**每个 tick 都重申当前模式**，包括常亮模式。

> 这其实是个更好的模型：灯**持续**服从策略，而不是只在状态跳变时才服从。
> 于是任何别的写这些寄存器的东西（按键反馈、未来的效果）都无法把灯留在策略没要求的状态里。
> 代价是常亮模式每 tick 一次 I2C 写，和呼吸模式同量级。

**顺带把待机灯调亮**：`B220_POLICY_IDLE_LEVEL` 从 `0x1F`（12%）改成 **`0x55`（33%）**。
理由：这是用户几乎一直看到的那盏灯，12% 只能"证明设备开着"，太弱以致于按键闪一下都不明显。

### ② 10% 音量太低 —— 我改错了方向，被自己的数值复算抓回来

用户要求：**10% 应该达到原来 20% 的响度**。

我第一次改的是 **dB 范围**（96 → 63）—— **方向完全错了**：范围变小会让**每一档都更轻**
（10% 从 −71 dB 掉到 −78 dB）。而且我用解析式 `96*(0.1^1.7)` 核算，与代码里**整数表**的实际
取值不符（表把 `x^0.7` 量化到 0..64），所以纸面推导和实测都对不上 —— 是主机上按代码同款整数算法
复算才把矛盾暴露出来。

**正确的杠杆是"曲线形状"（指数），不是范围**：要**抬高底部同时钉住顶部**，只能改指数。

| 指数 s（`x^s` 的 sub-exp） | 10% | 20% | 50% | 70% | 100% |
| --- | --- | --- | --- | --- | --- |
| 0.7（原） | −71 | −59 | −32 | −17 | **+6** |
| **0.4（采用）** | **−53** | −41 | −17 | −8 | **+6** |

10% 从 −71 dB 抬到 **−53 dB**（原来 20% 是 −57 dB，很接近），**顶部仍是 +6 dB 不变**。
表值 `round((i/32)^0.4 * 64)`，末项保持 64 以保证 100% 正好落在量程顶端。

## 2.9a-pre-1 音量：改成感知曲线，双击改为立即生效（2026-10-11）

用户反馈两条：**"音量越大，每跳 10% 听感上上升特别大"**、**"双击延迟不好，改成立即生效"**。

### 问题一：恒定 +10 dB 的直线

原实现 `gain = vol - 90` 把 100 个刻度均匀摊在 100 dB 上 ⇒ **每一步恒定 +10 dB**
（= 幅度 ×3.16）。响度感知近似对数，所以固定 10 dB 在**任何**音量都是 3.16 倍跳跃，
到了高音量区既刺耳、又逼近 DSP 的 **+6 dB 饱和**。

### 原厂不是这么做的（反汇编 `0x401256D8`，本次新读出）

```
if (vol > 99) vol = 100;
index = vol / 10                       <- 只有 10 档，不是 100 档（魔数除法 0x66666667）
gain  = table[index]                   <- 查表，不是线性
写 0x238 / 0x23A（左右增益，8 位符号扩展）
if (reg 0x0014 == 0x200) {
    写 0x24E
    0x494 <- vol >= 80 ? 0x16C3 : 0x0666   <- ★ 第二级衰减，高音量区换档
    0x49A <- vol >= 80 ? 0x0001 : 0x0002
    软复位
}
```

两个重要事实：

1. **原厂最高档不是 +10 dB**：它 boot 灌入的配置记录把 `0x238` 留在 `0xF1 = -15 dB`，
   自己的播放路径写 `0xEC = -20 dB`。**+10 dB 根本不在它的量程里** —— 是本移植自己加出来的；
2. **`vol ≥ 80` 时它换用第二级衰减寄存器 `0x0494/0x49A`** —— 这就是 PART 2 里记过、
   但**从未实现**的粗/细两段（索引 330/333 落在被漏掉的配置记录尾部）。

### 本次修法：感知曲线（并在注释里写明"这是近似，不是原厂表"）

```
gain_dB = -90 + 96 * (vol/100)^1.7
```

- 用 33 项 `x^0.7` 表 + 线性插值做**整数幂**，不引入浮点/libm，曲线严格单调；
- 锚在 `-90 dB`（0 仍是静音），顶部落在 **+6 dB**（DSP 真正能给出的最大值），
  不再索要 +10 dB 被限幅；
- **越往上每步越小**（实测数值，主机复现）：

| 音量 | 增益 | 相邻 10% 步长 |
| --- | --- | --- |
| 10 → 30 | −71 → −47 dB | +19、+14、+10 |
| 40 → 70 | −38 → −15 dB | +9、+8、+6 |
| **80 → 100** | **−8 → +6 dB** | **+3、+3、+5** |

> 注意：`0x0494` 那一段**仍未实现**。所以这是"在没有第二级衰减的前提下最诚实的做法"；
> 等哪天把粗/细两段做出来，应该改成直接复刻原厂表。

### 问题二：双击延迟

原实现为了"双击不会先走一步再跳"，把单击步进**推迟整个双击窗口（400 ms）**。
对这台机器是**错的取舍**：用户绝大多数操作是单击，却让每次单击都背 400 ms 延迟。

改成：**第一次按下立即步进**；窗口内同键第二次按下 ⇒ 升级为"跳到端点"
（那一小步被跳转吸收，看不出来）。实现也从定时器换成**两个变量**
（`s_last_volume_us`），不必创建/取消/清理任何东西。

## 2.9a-pre0 亮度与音量的持久化（2026-10-11）

用户要求："修改声音和背光亮度后保存到 flash，下次启动加载。"

### 音量：**框架本来就在存，但从来没被应用**（真 bug）

`AudioCodec::Start()` 只做一件事：把 `Settings("audio"/"output_volume")` 读进
`output_volume_`。它**不调用 `SetOutputVolume()`** —— 而在这台机器上，真正把电平写进
DSP（`HBI 0x0238/0x023A`）的正是这个函数。

后果很隐蔽：**UI 和 NVS 里的音量被恢复了，喇叭的实际电平却是 boot 配置记录里那个固定值。**
看起来"设置是持久的"，实际每次开机音量都不一样（跟上次调过什么无关）。

### ★★ 上机又抓到一个：两个默认值打架，屏幕被"拉下去"

第一版（已提交为 `7b554cf`）上机日志：

```

53: backlight: applied the saved brightness 100% at start-up (no fade)
54: Backlight: Set brightness to 75                        <- 基类随后把它拉回它自己的默认值
56: backlight 99% -> DIM3/DIM4 = 0xFC                     <- 并且开始缓动下降，一路到 75%
```

**根因**：`Backlight::RestoreBrightness()` 自己也会读同一个 NVS 键，而它的兜底默认是 **75**。
用户从没存过亮度 ⇒ 它走兜底 ⇒ **把板级的 100% 覆盖掉，还带一次可见的缓动**。

**这属于"我调用了两次恢复"** —— 我在 `ApplySavedBrightnessNow()` 之后又调了基类的
`RestoreBrightness()`，以为它是"同步基类状态"的无害操作，实际它是**第二次恢复**，
而且用的是另一个默认值。

**修法**：只由板级方法负责恢复；并且用**哨兵默认值**区分"从没存过"和"存过"：

```cpp
static constexpr int kNeverStored = -1;                   // Settings 没有"键是否存在"接口
const int stored = settings.GetInt("brightness", kNeverStored);
if (stored 无效) { percent = 板级默认; settings.SetInt("brightness", percent); }  // 落盘一次
else            { percent = stored; }
```

之后"没存过"这种状态就不存在了，基类再也无法用它的 75% 覆盖。同时**不再调用
`Backlight::RestoreBrightness()`**（注释里写明了原因，避免以后有人"顺手加回来"）。

> **教训：同一个设置不要接两套恢复逻辑。** 两处默认值（板级 100% / 框架 75%）
> 必然打架，而且症状是"屏幕亮度不对"这种看起来像硬件问题的现象。

修复前这里只有第一行 —— NVS 里有值、UI 显示正确，而喇叭电平是 boot 配置记录的固定值。

### ★ 这里又踩了一次同一类陷阱

我先把 `SetBrightness()` 写成派生类的 `override` —— **编译直接报错**：
`Backlight::SetBrightness()` **不是虚函数**，`RestoreBrightness()` 内部调用它永远是基类版本。
（和前面 `WifiBoard::OnNetworkEvent` 完全同一类问题：**非虚函数 + 基类内部调用 = 派生版本永不执行**。
两次都是靠"加 override 让编译器报错"或"加日志发现没打印"才发现的。）

改法：**在开局时预置 `brightness_` 到目标值**，让基类的 `SetBrightness()` 命中
`brightness_ == brightness` 的提前返回 —— **缓动定时器根本不会启动**。

**为什么必须避免那个缓动**：`Backlight::SetBrightness()` 只存目标值，真正的写入发生在 5 ms
定时器里、**从当前值逐级**进行。开机时当前值是 **0**，于是"恢复保存亮度"会先往 `0x23` 写一百个
近黑值 —— 而**低值是实测会关掉这块屏的**。用户会看到每次开机屏幕先黑、再慢慢爬亮，还要多花
两百次 I2C 写。**缓动适合"用户主动改亮度"，不适合"开机恢复设置"。**

实测 `0xFF`（100%）最亮且无异常，所以出厂默认改为满亮度。用户在系统里改过之后，
NVS 里的值才是准；`config.h` 的 `B220_LED_BACKLIGHT_DEFAULT_PERCENT` 只是**首次开机的默认**。

## 2.9a-pre ✅ RGB 指示灯通了（2026-10-10 晚，实测定性）

### 一句话

**六颗 RGB 并联、共阳，R/G/B 分别接 AW9106B 的 OUT0/OUT1/OUT2，对应 `0x20/0x21/0x22`。**
它们之前不亮的原因**不是"没接"**，而是缺两笔**输出驱动配置**（`0x15`/`0x16`）+ 组 A 的
**LED 驱动位**。这三样配好之后：`0x20`→红、`0x21`→绿、`0x22`→蓝、三路一起→白。

### 走通的那一组寄存器值（已实机验证）

| 寄存器 | 值 | 作用 |
| --- | --- | --- |
| `0x12` GPMD_A | **`0x0A`** | **GPIO 位(0x02) \| LED 驱动位(0x08)** —— 关键 |
| `0x15` | `0x1B` | 输出驱动配置（本移植此前**从未写过**） |
| `0x16` | `0x08` | 同上 |
| `0x11` CTL | `0x12` | 参考实现点灯时收敛到的值 |
| `0x14` EN_BRE | `0x00` | 常亮（非呼吸） |
| `0x20/0x21/0x22` | `0x00..0xFF` | R/G/B 亮度，DIMx 是 **8 位** |
| `0x23/0x24` | `0x80` | **LCD 背光**（不可低于此值） |

### `0x0A` 是这次的真正突破口

规格书 9.2 / 表 4、5：**OUTx 上电默认是 GPIO，要靠 `GPMD_A`/`GPMD_B` 切到 LED 驱动模式**。

- 本移植一直把 `0x12` 钉在 `0x02`（GPIO 位）—— 因为 AW8737S 的 SHDN 在 **组 A 的 OUT1** 上，
  而功放走查证明只有 `0x02` 能让 SHDN 动（`0x08` 会让功放没声音，所以原厂尾段的
  `{0x12, 0x08}` 曾被本移植删掉）；
- 于是 OUT0/OUT2 **一直是普通 GPIO**，根本不是恒流灌电流口 —— 这才是"写 DIM 不亮"的根因；
- **`0x0A` = 两个位都置**：OUT0/OUT2 进 LED 驱动模式点灯，OUT1 仍是逻辑输出驱动 SHDN。
  **实测：灯亮，且喇叭照样有声音。**（文档里记了很久的"从未测试"组合，这次测掉了。）

### DIMx 是 8 位，我之前的"上限 0x3F"是错的

规格书 9.2：「8-bits DIMx can be configured to 256 levels, from 00H to FFH」，另有
`ISEL[1:0]` 选四档电流范围（默认 0~37mA）。

参考项目的 `MODOU_KEY_LIGHTS_MAX_BRIGHTNESS 0x3f` **只是它自己选的暗亮度**，我误当成硬件上限。
实测阶梯 `0x0F → 0x3F → 0x7F → 0xBF → 0xFF` **依次变亮、无钳位异常** ⇒ `0xFF` 才是满亮度。
`B220_LED_BRIGHTNESS_MAX` 已改为 `0xFF`（改完之后编译器立刻报出三处 `brightness > 0xFF`
恒为假 —— 那是我原来那段 clamp 变成了死代码，已删除）。

### 我在这件事上错过的三个结论（保留，作为方法论的反面教材）

| # | 当时的结论 | 实际 |
| --- | --- | --- |
| 1 | "`0x20/0x21/0x22` 本机未接，屏幕没反应" | 它们是 **RGB**，只是没配驱动；而且背光在 `0x23/0x24` |
| 2 | "指示灯不在 AW9106 上，去别的总线/GPIO 找" | 就在 `0x20/0x21/0x22` |
| 3 | "DIM 上限是 `0x3F`（照抄参考常量）" | 8 位，`0xFF` 满亮度；`0x3F` 只有 25% |

三个错误的共同点：**把"没反应"当成"没接"，把别人的常量当成硬件规格**。
真正解决它的是**用户用万用表量出的实际接线** + **与已验证实现做严格寄存器差集**
（差集只有 `0x15`、`0x16` 两个寄存器，一步就定位了）。

### 生产配置（本轮固化）

- `xiaomodou_b220.cc`：`B220_AW9106_GPMD_A_GPIO` 由 `0x02` 改为 **`0x0A`**（所有写 `0x12` 的地方
  统一用这一个常量，SHDN 脉冲逻辑 `0x0A→0x00→0x02` 原样成立、上升沿仍只有一个）；
  初始化序列新增 `{0x15,0x1B}`、`{0x16,0x08}`、`{0x14,0x00}`，并把 `0x20/0x21/0x22` 起始值改为 `0x00`；

  接口 `b220_led_set_color/pulse/show_temporary/set_idle_color`；
- 按键反馈带颜色：**录音键=白闪、音量+=绿闪、音量−=红闪**，全部非阻塞。

## 2.9b **真正的"开机卡住"**：按键任务忙等把 CPU 占死了（已修，2026-10-10）

### 现象（用户原话："这还不是初始化问题吗？不按按键就一直等"）

对，**这次是初始化卡住**——但不是 DSP，是**板级构造函数被按键任务饿死了**：

```
I (6104) b220-btn: ZL38063 key poller up: ...
W (6144) b220-btn: ignoring one unconfigured key 0x0301 ...      <-- 此后 57 秒一行日志都没有
E (26034) task_wdt: Task watchdog got triggered. ... - IDLE0 (CPU 0)
E (26034) task_wdt: CPU 0: b220_buttons                          <-- 看门狗直接点名
Backtrace: ... 0x4024108A (b220_buttons.c) ...
W (63374) b220-btn: key VOLUME_UP ...                            <-- 只有用户按了键才继续
```

注意时间线：`b220_led` / `b220-base` 的初始化日志**本来紧跟在 6104 之后**，却拖到 63374 才出现，
而且只在你按键之后 —— 说明**构造函数在 6104 之后就没能继续跑**，直到按键任务偶然阻塞了一下
（写日志）才让出 CPU。

### 根因：我把中断当成了"立即读"的触发器

```c
const bool irq_pending = (s_irq_count != last_irq);
const bool due = (now_us - last_poll_us) >= 10 ms;
if (!irq_pending && !due) continue;     // <-- 只有"没中断且没到点"才睡
```

GPIO38 是**只输入脚、没有内部上拉**（日志里 `gpio_pullup_en(89): GPIO number error` 就是这个），
开机时它读作 **0**：一条**没有驱动、悬空的线**在翻动，边沿中断几乎每轮都会触发 ⇒ `irq_pending`
**永远为真** ⇒ `continue` 之前从不 `vTaskDelay` ⇒ 任务**不睡**，把 CPU 0 占满。

后果连锁：IDLE0 被饿死 → 看门狗报警；构造函数（同为 CPU 0 上的任务）被饿死 → 板级初始化停住 →
**只有按键让任务阻塞在日志上时才继续**。这解释了你看到的一切。

### 修法

**中断不再参与控制流**：循环只按**固定 10 ms** 节拍走，`s_irq_count` 保留但**不参与判断**
（写注释说明为什么）、并且 `last_poll_us` 初始化成"已经过期"，让**第一次读立刻发生**。
中断本身还挂着（当活动提示、代价为零），但**即使这条线完全噪声化也不会再影响任何东西**。

另外新增一行**构造函数完成标记**，把"卡在初始化里"变成一眼可见：

```
I XiaoMoDouB220: board init complete: display, keys, indicator lights and the baseboard link
                 are up (application start follows)
```

### 教训（写给下一个改这里的人）

> **"中断只是提前一点"和"中断会让循环不睡"是两种完全不同的设计。**
> 前者安全，后者是 CPU 独占。在没有上拉、没有驱动源的引脚上，
> **任何以边沿为条件的循环都可能变成忙等**。

## 2.10 初始化时间到底稳不稳（量化，2026-10-10）

用 `tools/b220_boot_timing.py` 扫了 `logs/boot-*.log` 全部启动记录，把关键节点的时间差算出来：

| 阶段 | 各次启动的实测值 | 结论 |
| --- | --- | --- |
| GPIO19 复位脉冲时刻 | 1264~1404 ms | 稳（±140 ms） |
| **DSP 主机引导（复位 → 应用 READY）** | **4560 ms，绝大多数启动完全相同**（4560/4570；个别 5030/5040） | **非常稳** |
| 其中：3699 条固件记录上传 | 3640~4110 ms | 稳 |
| DSP 复位 → codec 启动 | **9870 ~ 77450 ms** | **差别巨大** |
| Wi-Fi 拿到 IP | 16544 ~ 80694 ms | **差别巨大，且与上一行同步变化** |

**结论：慢的不是我们，是 Wi-Fi/云端连接。** 每次启动，codec 启动时间与"Wi-Fi 拿到 IP"的时间
**差几乎恒定在 2.1~2.6 秒**。也就是说：

- 板级与 DSP 那条路是确定性的（4.56 s 的固件上传是固定成本，无法省，除非放弃音质）；
- 看到的"有时快有时慢"完全来自**路由器/AP 关联与 DHCP 的耗时**（16 s 到 80 s 不等，
  同一台设备同一固件）；
- 这一条**不需要也不应该改固件**：把 DSP 引导推迟到网络之后只会让"能对话"更晚。

> 顺带一个可以省时间的点：如果不想每次开机都花 4.6 s 重灌 DSP 固件，可以研究
> "DSP 已经跑着就跳过上传"（读 `reg 0x0014 == 0x0200` 判定）。但注意**软复位/掉电后 DSP 一定
> 是空的**，所以只在"浅重启"（ESP32 复位而 DSP 未断电）时才有意义，收益有限、分支变多，暂不做。

| 位 | 名称 | 取值 | 依据 |

| 4 | **模式** | **1 = 慢闪、2 = 中闪、3 = 快闪**；`0` 与 `4~8` **无反应** | 用户扫描 0→8 |

### 两个字段的交叉实测（用户）

| 模式(4) | 长度(3) | 现象 |
| --- | --- | --- |
| 1 | 1000 | 慢闪两三下后灭 |
| 2 | 1000 | 中闪，频率不变、总时间随长度变长 |
| 3 | 1000 | 快闪 |
| **1** | **≥ 4000** | **常亮** ✅ |
| **3** | **≥ 4000** | **持续变色闪烁、不熄灭** |
| 0 / 4~8 | 任意 | 无反应 |

### 结论：**"常亮" = 长度 ≥ 4000 + 模式 1**

- **长度 < 4000** 是一个**会播完的动画**（所以"闪两三下就灭"）；
- **长度 ≥ 4000** 时底座把它当成"持续"处理，模式 1 常亮、模式 3 无限变色闪烁；
- **因此灯不需要靠重发维持** —— 早期版本每 900/1000 ms 重发一次，
  反而是**每次重发都重启动画**，这才是"闪烁"的真正来源。

### 最终实现

```c
#define B220_BASE_LIGHT_ON_MS      4000   /* 常亮阈值 */
#define B220_BASE_LIGHT_ON_MODE       1   /* 1 = 慢闪档，配合长长度即常亮 */
#define B220_BASE_LIGHT_REPEAT_MS  3000   /* 仅作保险，远长于动画重启的节奏 */
```

- 前灯（RGB）用第 2、3 组元组，尾灯（单色红）用第 4、5 组，**同一条帧**写出（避免互相覆盖）；
- **不亮的那组把长度写 0**（参考项目就是这么关灯的）；
- 长度 4000 自带常亮，所以重发周期放到 3000 ms 只是"防止帧本身过期"，不会重启可见动画。

这套参数顺带给出了**可直接使用的效果**（若以后需要）：

| 效果 | 长度 | 模式 |
| --- | ---: | ---: |
| 常亮 | ≥4000 | 1 |
| 慢闪 | 1000~3000 | 1 |
| 中闪 | 1000~3000 | 2 |
| 快闪 | 1000~3000 | 3 |
| 无限变色闪烁 | ≥4000 | 3 |

## 2.11p ★ 灯光：前后分组、必须**周期性重发**（2026-10-11）

### 用户报告

> "目前通过语音打开前灯或调整前照灯颜色后，**约 1 秒后会自动关闭**"

### 原因：和运动同一条规律 —— **时长字段被截到约 1000 ms**

参考项目的灯帧用的是**时长 2000**，那是为"会遵守该字段"的硬件写的。
而本机已实测：**时长字段上限约 1000 ms**（最早在运动那边发现的"最长只有 1 秒"）。

⇒ **一条灯帧 = 亮 1 秒**。要常亮就必须**重发**，和运动完全同一个道理。

### 参考项目的灯帧结构（照抄）

| 灯组 | 帧头 | 哪些元组 |
| --- | --- | --- |
| 右前单灯 | `(4,1,3,1)` | 第 **2** 组 |
| **前灯对** | `(4,1,0,1)` | 第 **2、3** 组（同一颜色写两次） |
| **尾灯对** | `(4,1,0,1)` | 第 **4、5** 组 |

### 实现：灯光成为一个"期望状态 + 保活任务"

- `b220_baseboard_lights()` **只设置期望状态**（前灯开/关+颜色、后灯开/关），不再直接发一条帧；
- 一个 `lights_task` **每 900 ms 重发一次**当前状态（帧内时长用上限 1000 ms）；
- 两组都关时**不发任何帧**，所以待机时它只占一个任务、不产生流量；
- **`{BASE+STOP}` 也会关灯**，否则"停止"之后灯还会自己回来。

### 前 RGB / 后单色红

用户明确：**前灯是 RGB、后灯是单色红 LED**，所以两者**分开控制**：

```
front: white / red / yellow / green / blue / deepblue / purple   (RGB)
rear : rear_red                                                   (单色红，只有红/灭)
off        -> 两组都关
front_off / rear_off -> 单独关一组
```

MCP 工具 `self.base.lights` 的描述已据此改写，明确告诉模型"后灯只有红，且灯会保持不自动关"。

**注意**：前灯"RGB"目前是通过**预设颜色索引**访问的（白/红/黄/绿/蓝/深蓝/紫），
参考项目也只有这些预设。**任意 RGB 数值**是否可行**尚未验证** ——
若需要真正的任意配色，要先确认真彩帧的格式。

## 2.11o ★★ 速度位会**取消转弯** —— 速度必须按方向分开

### 现象

定标后刷入，用户报告：**`{BASE+MOVE,left,...}` 和 `{BASE+MOVE,right,...}` 仍然是前行**，
日志里的帧看起来完全正确：

```
move: left  (code 2, turn 90, speed 255)
  frame: AT+CMD=(1,1,3,1),(2,300,90,255,1),...
```

### 原因：速度 255 把两轮速差抹平了

对照用户自己的实测：

| 帧 | 速度 | 现象 |
| --- | ---: | --- |
| `(2,300,90,**90**,1)` | 90 | **明显左转** |
| `(3,300,90,**90**,1)` | 90 | **明显右转** |
| `(2,300,90,**255**,1)` | 255 | **前行** |
| `(3,300,90,**255**,1)` | 255 | **前行** |

而用户此前描述过速度位的规律："**>110 时两轮速度都更快，但速度也变得接近**"。

⇒ **差速转弯的本质就是两轮的速度差**，而**速度位一大就把两轮拉齐**，转弯随之消失。

**这是"默认速度 255"与"能转弯"之间的直接冲突** —— 我上一版把两者放在同一个速度上，
所以方向映射明明正确、车却只走直线。

### 修法：速度写进方向表，每个方向一个值

```c
{"forward",    2, 50, 255},   /* 直行用 255：拉齐正是我们想要的 */
{"backward",   1, 50, 255},
{"left",       2, 90,  90},   /* 转弯用 90：低于两轮开始拉齐的阈值 */
{"right",      3, 90,  90},
{"spin_left",  6, 50,  90},
{"spin_right", 7, 50,  90},
```

调用方给的速度（如 `{BASE+MOVE,left,200,...}`）**可以覆盖**表里的值，方便台架测试；
不给就用表里的 —— **因为表里的值才是"能转弯"的那个**。

### 教训

**同一个参数在不同动作里需要不同的值**，而"默认值"这种一处配置的做法在这里不成立。
更要紧的是：**用户的实测数据里早就写着答案**（"转弯是在速度 90 下测的"、
">110 两轮趋于接近"），我却在实现时把速度统一成了 255 —— **有数据却没有按数据实现**。

## 2.11n ★★★★★ 底座控制**全部定标**（2026-10-11 收尾）

### 元组第 3 位 = **转弯力度**（不是转向角）

用户逐值测试（码 2、速度 90）的完整结论：

| 第3位 | 现象 |
| ---: | --- |
| 0 | 两轮同速 |
| 10→50 | 右轮渐快、左轮渐慢 |
| **60 及以上** | **只有右轮转**（左轮停） |

再叠加"码 3 / 码 0"的对照，得到**一条自洽的规则**：

> **第 3 位越大，转弯越急；转弯内侧的轮子减速。**
> 50 ≈ 几乎直行，**90 = 差分能达到的最急转弯**（一个轮停，**不会反转**——
> 用户把扫描推到 −90，现象无变化）。

⇒ **第 3 位就是"转弯半径旋钮"**：50 直行 / 70 缓弯 / 90 最急。
再小的半径只能靠**原地转**（码 6/7，一轮正一轮倒）。

### 最终映射（全部用户实测）

| 语音/工具 | 码 | 第3位 | 实测依据 |
| --- | ---: | ---: | --- |
| `forward` | 2 | 50 | "稍左偏"（最接近直线） |
| `backward` | 1 | 50 | 后退、两边同速 |
| `left` | 2 | 90 | **明显左转**，左轮慢 |
| `right` | 3 | 90 | **明显右转**，右轮慢 |
| `spin_left` | 6 | 50 | **原地左转** |
| `spin_right` | 7 | 50 | **原地右转** |

**默认速度 255**（用户指定）；`{BASE+STOP}` 已确认**能立刻停住**。

`forward` 用码 2 而非码 0：两者偏移量相同（左/右），码 2 与 `left` 同码，
所以**直线微调只需改一个数字**。要调就改 `b220_direction_t` 里 forward 的第 3 位。

### 速度位（元组第 4 位）的两个作用

用户扫描 20→200 的观察："**都有反应**，≤110 时右轮明显快于左轮；>110 两轮都更快、
且速度趋于接近"。⇒ 低值利于**急转**（速差大），高值利于**直行**（趋于同速）。

### `{BASE+RAW}` 的两种写法（用户发现的问题已修）

用户从日志里发现：`{BASE+RAW,0,300,0,90,10}` 被解析成帧头 `0,300,0,90` +
元组 `10,...`，**(1,1,3,1) 丢了**，发出畸形帧。

**靠数字个数猜是行不通的** —— 按"≥5 个即元组"解析会把 9 个数字的旧写法
（`1,1,3,1,...`）也当成元组。所以现在**显式声明**：

```
{BASE+RAW,T,<元组字段...>}      数字是元组，帧头固定 1,1,3,1
{BASE+RAW,H,<四个帧头>}         数字是帧头
{BASE+RAW,<10个以上数字>}       帧头 + 元组（旧写法，保留）
```

帧缓冲同时从 192 增到 **224**（两元组帧恰好是 192，没有余量）。

### 方法上的教训（最贵的一条）

这一轮我**连续两次用推理代替测量**（"左右反了"就换码、按一个码的表外推另一个码），
结果**把已经验证可用的版本改坏了**。有效的做法是：
**一次只改一个字段、用现象确认、把结论记成表** —— 也就是用户要求的
"编个可以调整多个参数的指令，我来测试"。

## 2.11m ★ `{BASE+RAW}` 复刻帧确认码 2 = 右轮；**并修掉"STOP 停不住"**

### 逐字段复刻参考帧的结果

```
{BASE+RAW,AT+CMD=(1,1,3,1),(2,300,50,30,1)}
```

用户报告："**右轮子一直正转，左轮子不转**"。

⇒ **码 2 = 右轮正转**（单轮），与之前 `{BASE+REF,2}` 的结论一致。
⇒ 参考帧形态**逐字段复刻可用**，`{BASE+RAW}` 达到了"不用再改固件就能试任意组合"的目的。

### ★ 一个真问题：`{BASE+STOP}` 停不住正在跑的测试任务

日志：

```
W (237557) b220-base: RAW: done - in place, arc, or nothing?   <- 我自己 5 秒窗口到期
I (237617) b220-base-ctl: stop (nothing was moving)
```

用户："**发送多次 {BASE+STOP} 后才停**" —— 实际上 STOP **一次都没生效**，
是**我的 5 秒窗口自己到期**才停的。

**根因**：`{BASE+STOP}` 走正常路径（`b220_baseboard_stop()`），而台架任务（RAW/HOLD/DIRS/SWEEP）
**自己直接发帧**，两者之间**没有任何联系**。于是：

> **一个会持续发运动帧的任务，任何 STOP 都打断不了它。**
> 在真车上这就是"停不下来的车" —— **属于故障，不是不便**。

**修法（两处）**：

1. 新增**停止代数计数器** `b220_baseboard_stop_generation()`：`stop` 时自增；
   台架循环在开始前记下当前值，**一旦发现变化就立刻退出**。
   用**计数器而非布尔标志**，是为了让"循环开始之前就到达的 stop"同样有效，
   也避免连续两次 stop 被合并成一次。
2. `b220_baseboard_stop()` 现在**立即清 `s_moving`**（原来要等控制任务下一次 tick），
   否则 stop 之后还会多发出一帧运动。

**我自己在这轮里还犯了一个错并当场修掉**：第一版把 RAW 的循环条件写成
`b220_baseboard_is_moving()` —— 但 RAW 是**旁路路径**、从不置 `s_moving`，
所以循环**一次都不执行**，等于把命令改成了空操作。
这个错误正好说明了为什么需要独立的"停止代数"。

### 教训

**安全机制必须覆盖所有能发帧的路径**，而这条路径当初是为了排查方便随手加的。
"测试通道绕过正常路径"在功能上无害，但在**停止**上是危险的 ——
因为正常路径的停止**管不到它**。

## 2.11l 速度提升 + "转"与"原地转"分开（2026-10-11）

### 速度

用户验收："**指令都对了，但是速度都很慢**"。原因清楚：元组的**速度字段一直是参考的 30**
（前几轮我甚至把它锁死、不写进帧），而现在知道那个字段是有效的。

于是速度成为真正的参数：

| 位置 | 用法 |
| --- | --- |
| 本地通道 | `{BASE+MOVE,<方向>,<速度>,<毫秒>}` —— **第 2 个字段就是速度** |
| MCP 工具 | `self.base.move` 的 `power`（范围放宽到 **10..255**，默认 30） |

**默认仍是 30（实测值）**，要快就显式给：候选 **60 / 100 / 150 / 200 / 255**。
`B220_BASE_SPEED_MAX = 255` 封顶，避免误传一个失控值。

### "转"与"原地转"分开

用户要求："**说原地左右转的时候再原地转，不说原地的时候正常转就行**"。
控制码天然支持这个区分，因为两者的运动学不同：

| 控制码 | 两轮状态 | 运动学 | 对应说法 |
| ---: | --- | --- | --- |
| **2 / 3** | **一轮正转、另一轮不动** | **有净前进量** ⇒ 边走边转（弧线） | 「左转」「右转」 |
| **6 / 7** | **一轮正转、另一轮倒转** | **净前进量为零** ⇒ 原地打转 | 「**原地**左转/右转」 |

所以最终映射：

```
forward      0     前进
backward     1     后退
left         3     弧线左转（左轮转，右轮不动）
right        2     弧线右转（右轮转，左轮不动）
spin_left    6     原地左转
spin_right   7     原地右转
```

**弧线用单轮（2/3）而不是把两轮速度设成不同** —— 单轮是这个协议里**已验证**的用法
（参考项目的"左轮慢转/右轮慢转"就是它），而"两轮同时但速度不同"从未验证过。
**优先用已验证的形态**，这是本项目反复吃过的教训。

MCP 工具的描述也据此改写：明确告诉模型 `spin_left`/`spin_right` 是**原地**，
**只有用户说"原地"时才用**，否则用 `left`/`right`。

## 2.11k ★★★★★ **底座控制码确定，转向解决**（2026-10-11）

### 决定性的测试：`{BASE+REF,<码>}` 扫 0..10

用户逐个测试参考帧形态、**只改元组第 1 位**：

| 码 | 动作 | | 码 | 动作 |
| ---: | --- | --- | ---: | --- |
| **0** | 双轮正转（前进） | | **5** | 左轮倒转 |
| **1** | 双轮倒转（后退） | | **6** | **左倒右正** ← 原地转 |
| **2** | 右轮正转 | | **7** | **左正右倒** ← 原地转 |
| **3** | 左轮正转 | | 8 / 9 / 10 | 无反应 |
| **4** | 右轮倒转 | | | |

**编码完全自洽**，这正是它可信的原因：`4 = 2 的反向`、`5 = 3 的反向`、`6 = 4+3`、`7 = 2+5`。
**六个动作全部有解**：前进 0、后退 1、原地左转 6、原地右转 7，以及单轮 2/3/4/5。

### 生效的帧（唯一能工作的形态）


**五个字段一个都不能按我们自己的想法改** —— 这是本项目最贵的一课：

| 字段 | 我们曾一直发的 | **能工作的值** |
| --- | --- | --- |
| 帧头 | `(9,1,0,1)` | **`(1,1,3,1)`** |
| 第 1 位 | mode 0..5 | **控制码 0..7** |
| 第 2 位 | 1000 | **300** |
| 第 3 位 | 90 | **50** |
| 第 4 位 | 200 | **30** |
| 第 5 位 | 0 | **1** |

**六个字段里我们改过五个，而正确的帧一个字段都不该改。**
`(9,1,0,1)` + `(mode,1000,90,200,0)` 这种形态下，28 组模式/角度组合**全部只走直线**，
连元组第 1 位写成 0（本该空转）都照样前进 —— 当时就应该意识到"**这整套参数都没被读**"，
而不是继续在模式表和转向角上找。

### 最终方向表（`b220_baseboard.c`）

| 语音/工具参数 | 控制码 | 动作 |

| 步 | mode | steer | 帧头 | **第5字段** | 结果 |
| ---: | ---: | ---: | --- | ---: | --- |

### 再看参考帧：第 1 位是"通道/方向"

```
AT+CMD=(1,1,3,1),(2,300,50,30,1),...     左轮
AT+CMD=(1,1,3,1),(3,800,90,30,1),...     右轮
```

把两轮结果和我们自己的观察合起来：

| 元组第 1 位 | 含义（推断） |
| ---: | --- |
| 1 | 前进（我们 mode 3 + reserve 0 走的形态） |
| 2 / 3 | **右轮 / 左轮各自正转**（参考的两轮通道） |
| 0 | 停止 |

**所以这套底座是靠"每轮一条帧"来转向的** —— 一条帧只能带一个元组，两轮机动必须**两条帧**。

### 转向于是变成算术

| 左轮值 | 右轮值 | 结果 |
| --- | --- | --- |
| 2 | 3 | **原地转**（两轮反向） |
| 2 | 0 | **只左轮转 ⇒ 绕左轮弧线** |
| 0 | 3 | 只右轮转 |
| 2 | 2 或 3 | 直行 |

参考文档说"独立左右轮方案不够稳"，但**单帧 28 组测试一次都没转过** ——
所以这条路必须试，它很可能是唯一能转的路。

### 新增 `{BASE+WHEEL,<左轮值>,<右轮值>}`

每帧一条、两条同发、重复到 4 秒窗口后一起停：

```
{BASE+WHEEL,2,3}    原地转（两轮反向）
{BASE+WHEEL,2,0}    只左轮 → 绕左轮弧线
{BASE+WHEEL,0,3}    只右轮
{BASE+WHEEL,2,2}    直行（对照）
```

**下一步验证顺序**：

1. `{BASE+WHEEL,2,2}` —— 两个轮子是否都转、是否直行（先确认通道 2/3 都有效）；
2. `{BASE+WHEEL,2,0}` 与 `{BASE+WHEEL,0,3}` —— 分别确认是哪个轮子；
3. `{BASE+WHEEL,2,3}` —— **原地转是否成立**（这决定转向能不能做）。

**换句话说：这个移植从一开始就在发参考项目"放弃转向"之后的那种帧，然后奇怪为什么轮子不转向。**

| `right` | mode 3, steer 170 | 后退 |

**关键线索**：`backward` 和 `right` 都表现为后退 ⇒ **mode 3 + steer 170 是后退**。
而 `right` 当时正是 mode 1 + steer 180，"右转变成后退"就是它造成的 ——
**mode 1 是本机唯一出现过后退的模式**。

### 修正后的方向表（按实测 + 镜像对称推理）

```
forward     mode 3, steer 90   实测前进
backward    mode 1, steer 170  实测后退（唯一出现过后退的组合）
left        mode 0, steer 50   弧线；由"left 是 mode 0"这一实测符号推出
right       mode 1, steer 50   弧线；镜像对称（left 的镜像必须是 mode 1 + 同角度）
spin_left   mode 0, steer 0    原地转，**未验证**
spin_right  mode 1, steer 180  原地转，**未验证**
```

设计取舍：**`right` 刻意不再用 mode 1 + 170**（那会后退）。宁可"转得不对"，
也不能出现"让它右转、它却倒车"—— 后者危险得多。

### 新增能力

- **`spin_left` / `spin_right`**：原地转，与弧线转向分开命名（用户明确要求两者都要）；
- **MCP 工具** `self.base.move` 的 `direction` 现已包含这两个；
- **`{BASE+MOVE,...,[,mode,steer]}`**：可选的第 5、6 个字段直接指定原始 mode 与转向角，
  这样 DIRS 找到的候选可以**单独、长时间**复验，**不必重新编译**；
- **`{BASE+DIRS}` 扩到 20 步**，分三段：
  1. 4 个直行模式（找后退）；
  2. 8 个转向候选（弧线/原地混在一起，看哪个真转）；
  3. **8 个原地转候选**（mode 0/1 × steer 0/15/90/170/180），窗口 6 秒 ——
     原地转很好认：**两轮反向、机身绕中心旋转、位置不移动**。

## 2.11f ★★★★ 连续运动**已解决**：帧 1000 ms + 每 900 ms 重发

### 扫描结果（用户报告）

> "**7个测试，都是连续前进，前进约3秒**"

| 步骤 | 字段 | 间隔 | 速度 | 结果 |
| ---: | --- | --- | --- | --- |
| 1 | 1000 | **1000** | 255 | 连续 ✅ |
| 2 | 1000 | **900** | 255 | 连续 ✅ |
| 3 | 1000 | **800** | 255 | 连续 ✅ |
| 4 | 1000 | **600** | 255 | 连续 ✅ |
| 5 | **900** | 900 | 255 | 连续 ✅ |
| 6 | 1000 | 900 | **150** | 连续 ✅ |
| 7 | 1000 | 900 | 255 | ⚠️ mode 2 —— **仍然前进**（不是后退） |

每步正好约 3 秒 = 扫描窗口 3000 ms ⇒ **重复发帧确实维持了运动**。

### 抖动的原因定案

| 做法 | 字段 | 间隔 | 结果 |
| --- | --- | --- | --- |
| 早期版本 | **600** | 500 | **20 次抖动 / 10 秒** |
| 上一版 | 999 | 不重发 | **只动一次** |
| **本版** | **1000** | **900** | **连续** ✅ |

差别在**覆盖**：字段 600 ms 的一帧，扣掉底座自身处理时间后覆盖不住 500 ms 的节奏，帧与帧之间留空隙 ⇒ 抖动；
字段拉满 1000 ms、节奏 900 ms 时，下一帧**在上一帧结束前 100 ms 就已发出**，运动不再间断。

**这解释了当时那个"20 次"**：它既是"每 500 ms 重发一次"的计数，也是"每 500 ms 断一次"的证据 ——
**一个正在被自己人打断的运动。**

### 最终实现（`b220_baseboard.c`）

```
#define B220_BASE_FRAME_MS   1000   /* 字段拉满：底座会把更大的值截到这里 */
#define B220_BASE_REPEAT_MS   900   /* 比 1000 快 100 ms，形成重叠 */
```

- 正常移动路径：**运动期间每 900 ms 重发一帧**，到用户指定时长后发停止帧；
- **时长上限 10 秒**是"整个移动"的长度，不是单帧的（单帧被底座限制在约 1 秒）；
- 超时兜底仍在：移动本该结束后 900 ms 仍无状态变化 ⇒ 强制停止（防停止帧丢失）；
- `{BASE+SWEEP}` 保留（它现在是"走间隔"的台架工具）。

### 仍未解决：**mode 2 不是后退**

两次上机、六次尝试，**没有一个组合产生可靠的后退**：

| 尝试 | 结果 |
| --- | --- |
| mode 2, steer 90（文档写"后退"） | 前进 |
| mode 2, steer 50 | 前进 |
| mode 0 / mode 3 各角度 | 前进 |
| mode 1, steer 170 | **后退**（唯一一次，来自旧扫描第 7 步） |

文档说模式 2 = 后退，实测不符；唯一后退过的是 **mode 1 + steer 170**。
这与"模式由底座根据角度内部推导"的说法对不上 —— **这套固件的模式语义与文档不完全一致**。

**下一步可以这样定**：用扫描单独走 `mode 1` 与 `mode 2` 各自的多个角度（0/50/90/170），
看哪个组合让两个轮子**反向转**（真正的原地转或后退）。

## 2.11e ★★★ 机制定清了：时长的**单位是毫秒**、上限约 1 秒，速度最大 255

用户的实测（`{BASE+HOLD,forward,255,2000}`）：

> "只向前运动一次……第 3 个参数是速度，第 4 个参数是时长，**但是最长只有 1 秒**（1000 时）"

### 我此前的一个错误假设

我一直以为时长字段的单位是 **200 ms**（依据是参考项目"时长单位 200 ms"的说明，以及它写过 300~800）。

如果按 200 ms 算，参考的 300~800 就是 **60~160 秒**，与它自己文档里"运动帧有效期 800 ms"**自相矛盾** —— 我当时没注意到这个矛盾。

**实际上单位就是毫秒**，于是全部对上了：

| 观察 | 用"毫秒"解释 |
| --- | --- |
| 字段 600 + 每 500 ms 重发 ⇒ **20 次抖动 / 10 秒** | 600 ms 的帧给 0.6 秒运动，间隔 500 ms 的话两次之间有空隙 |
| 字段 999 + 不重发 ⇒ **只动一次** | 被底座截到约 1000 ms，然后就没有下一条了 |
| 字段 2000 ⇒ **最长只有 1 秒** | **该字段被底座上限截到 1000** |
| 参考项目"运动帧有效期 800 ms"、"同方向保持 600 ms" | 与"按毫秒计、约每秒重发"完全一致 ✅ |

### 由此得到的完整参数表（本机实测）

| 字段 | 含义 | 范围 |
| --- | --- | --- |
| 头部 | 运动/灯光掩码 | 运动 `9`，灯 `5`，参考的其它灯效果 `4`/`12` |
| 元组第 1 项 | 运动模式 | 0/1 转，2 后退，3 前进（4/5 右弯） |
| 元组第 2 项 | **时长（毫秒）** | **1..1000**（写更大也被截到 1000） |
| 元组第 3 项 | 转向量 | 90 直行；参考用 50/170 |
| 元组第 4 项 | **速度** | **最大 255**（我们此前一直叫它"动力"，且只给到 100 或 40） |
| 元组第 5 项 | 保留 | 0 |

### 因此：连续运动 = **按约每秒的节奏重发**

三次上机正好把区间夹出来了：

| 做法 | 结果 |
| --- | --- |
| 字段 600 + 每 **500** ms 重发 | **20 次抖动 / 10 秒**（帧太短，帧与帧之间有空隙） |
| **不重发** | **只动一次**（然后停） |
| **待测：字段 1000 + 每 900~1000 ms 重发** | 预期连续 |

**重叠是关键未知数**：在上一帧结束**之前**重发，可能是**平滑接续**，也可能是**重新开始**（那就会抖）。
所以 `{BASE+SWEEP}` 现在**专门走这个区间**：固定 mode 3 / 速度 255 / 字段 1000，
依次用 **1000 / 900 / 800 / 600 ms** 的间隔各跑 3 秒，另外三步做对照（字段 900、速度 150、mode 2）。

> 这次我不再猜 —— 上面那张"三次上机"的表就是**为什么区间只能测出来**：
> 500 太小、∞ 太大，答案在中间，而且**只有真机能说在哪**。

## 2.11d ★★ 根因：**每发一次运动帧，底座就重新执行一次动作**

### 上机结果（用户报告，`{BASE+SWEEP}`）

| 步骤 | 参数 | 步长 | 用户观察 |
| ---: | --- | --- | --- |
| 1 | mode 3, steer 90, 100% | 10 s | 间歇性**前进**，**20 次**，略右偏 |
| 2 | mode 2, steer 90, 100% | 10 s | 间歇性前进，**20 次**，略左偏 |
| 3 | mode 3, steer 90, 60% | 10 s | 间歇性前进，**20 次**，右偏更多 |
| 4 | mode 3, steer 50 | 2 s | 前进，**4 次** |
| 5 | mode 3, steer 170 | 2 s | 前进，**4 次**，略右偏 |
| 6 | mode 0, steer 50 | 2 s | 前进，**4 次** |
| 7 | mode 1, steer 170 | 2 s | **后退**，**4 次** |
| 8 | mode 2, steer 50 | 2 s | 前进，**4 次** |

### 数字就是答案

| 步长 | 我的刷新周期 | 刷新次数 | 用户数到的移动次数 |
| --- | --- | --- | --- |
| 10 s | 500 ms | **20** | **20** ✅ |
| 2 s | 500 ms | **4** | **4** ✅ |

**每一次刷新都对应一次新的动作** ⇒ **每一条运动帧都是一条完整指令，时长字段决定这一条持续多久；
重发它 = 命令底座"再来一次"**。

我原来的"心跳"思路（"运动帧只有 800 ms 有效期，所以要持续刷新"）**把"帧的有效期"理解错了**：
参考项目根本不是靠刷新维持运动 —— 它发**一条 300~800 单位（60~160 秒）的长帧**然后就不管了。

> **教训：一个周期恰好等于发送方刷新间隔的抖动，不是电机问题，是发送方在重启电机。**
> 用户"数次数"这个观察是本轮的关键 —— 它把"间歇性前进"这种模糊描述变成了**可对账的数字**。

### 修法

- **一次移动 = 一条帧**，时长**写进帧里**（字段是 200 ms 单位，`MAX_UNITS = 999`）；
- **删掉整个刷新循环**；
- **超时兜底保留**，但语义变了：现在是"这次移动本该结束之后又过了 X ms"才停 ——
  它仍是防止"停止帧丢失"的唯一保险（底座收不到停止会一直走）；
- `{BASE+SWEEP}` 也改成**每步只发一条帧**（否则扫描自己就是 bug 的来源）。

### 方向表：按实测更新

| 动作 | 模式 | 转向 | 实测 |
| --- | --- | --- | --- |
| `forward` | **3** | 90 | ✅ 前进（略右偏） |
| `backward` | **2** | 90 | ⚠️ 实测**前进** —— 应为后退，待定 |
| `left` | 0 | 50 | 前进偏转（尚不足以定死"左转"） |
| `right` | 1 | 170 | ⚠️ 实测**后退** —— 与预期不符 |

**转向语义仍未定论**：步骤 4~8 的观察更像"带转向的移动"而不是原地转，
而唯一产生后退的是 **mode 1 + steer 170**。这说明"原地转需要角度 <15 / >165"那条规则
**要么不是这么用的，要么这个底座的固件版本不同**。

**下一步**：在做无刷新修正后重新扫一次，重点看
1. 前进/后退是否变成**连续**运动（而非 20 次抖动）；
2. 哪个组合是**真正的原地转**（轮子反向转）；
3. 后退到底是哪个模式。

### 动力：**不要用 100%**

实测 100% 是能转的，而且很快。默认值保持 **40%**；用户要更快可以显式指定
（`{BASE+MOVE,forward,100,3000}`），但**不建议把 100% 当默认**。

## 2.11c 电机"有动作但不转"：时长与转向角两个嫌疑（2026-10-11 续）

### 现象

用户报告：模式修正 + 动力 100% 之后，**"能听到有电机的动作，但是没有转动"**。

这比"完全没反应"有用得多：**电机通电了**（能听到绕组励磁/驱动的声音），说明
底座收到了运动帧、也去驱动了电机 —— 问题在**扭矩或参数**，不在链路。

### 嫌疑一：我们的时长只有参考的百分之一

把参考项目**实测能跑**的帧和我们的并排放：

| | 时长字段 | 实际时长 | 动力 | 转向角 |
| --- | --- | --- | --- | --- |
| 参考"左轮快转" | **800** | **160 s** | 30 | **90** |
| 参考"左轮慢转" | **300** | **60 s** | 30 | **50** |
| 我们 | **3** | **0.6 s** | 100 | 90 |

也就是说参考是按**分钟**下发的，我们按**几百毫秒**。如果底座内部有**软启动/斜坡**，
我们可能在电机真正转起来之前就把帧撤掉了 —— **"有声音但不转"正好是这个形态**。

（我们当然不该学它跑 160 秒。但**2~3 秒**是合理的起点，这也是我把扫描里的步长设成
2000/3000 ms 的原因。）

### 嫌疑二：转向角可能一直在发给它无效的值

参考项目用到的转向角只有 **50 / 90 / 170** —— **没有 0 或 180**。
而模式表又写着"原地转需要角度 `< 15` 或 `> 165`"，**两者是矛盾的**：
说明"角度决定模式"是**底座内部**的逻辑，参考项目从没发过极点值去触发它。

我上一版把 `left` 设成 `steer=0`、`right` 设成 `steer=180` —— **很可能底座对这种组合没有定义行为**。
所以扫描里把参考用过的 50/170 也一起试。

### 新增 `{BASE+SWEEP}`：一次跑完所有嫌疑

```
{BASE+SWEEP}
```

它会自己按顺序试 8 组参数，每步 **2 秒**、步骤之间**强制停止**并留 0.7 s 间隔，
每步都打日志：

| # | 参数 | 想排除/确认什么 |
| --- | --- | --- |
| 1 | mode 3, steer 90, 100%, 2 s | 前进 + 更长时长 |
| 2 | mode 2, steer 90, 100%, 2 s | 后退 |
| 3 | mode 3, steer 90, 100%, **3 s** | 时长上限 |
| 4 | mode 3, steer **50** | 参考的左向角 |
| 5 | mode 3, steer **170** | 参考的右向角 |
| 6 | mode 0, steer 50 | 原地转（模式 0） |
| 7 | mode 1, steer 170 | 原地转（模式 1） |
| 8 | mode 2, steer 50 | 后退带转向 |

**扫描故意不走 `b220_baseboard_move()`** —— 它是台架工具，必须能试正常路径刻意限制的角度和时长；
但它**每步之间会停**，所以万一某步真的让轮子转了，也不会一路跑下去。

### 下一步取决于扫描结果

| 扫描结果 | 结论 | 动作 |
| --- | --- | --- |
| 某一步转了 | 找到可用参数 | 用它改写方向表（并记录哪一步） |
| 全部只响不转 | 不是参数问题 | 转向**机械/供电**：轮子是否卡死、底座是否需要更高电压的独立电源（我们只从 USB-TTL 取电的话，电机驱动可能带不动轮子） |
| 完全没声音 | 连驱动都没到 | 回到模式/头部字段排查 |

> 第三种情况特别值得留意：**电机是电流大户**。如果底座电机电源域与逻辑电源域分开，
> 而整机现在只靠调试用的 USB-TTL 供电，那么"有励磁声但转不动"就是**供电不足**的典型表现。
> 这一点在架上测试时尤其容易踩到。

## 2.11b 本地测试通道：不经云也能驱动底座（2026-10-11）

### 为什么需要它

两个具体理由，都不是"顺便加的"：

1. **方向约定还没验证**（`left`/`right` 用哪个转向极点、模式是否如文档）—— 而走语音验证，
   **每一次尝试都要一次完整的云端往返**（唤醒→识别→LLM→工具→下发），十几秒一轮，收敛很慢；
2. **网络本身坏掉时**，助手根本到不了工具 —— 而这恰恰是要排查的场景之一。

### 用法

往 UART0 发**一行**（串口终端或 telnet 皆可）：

```
{BASE+MOVE,forward,100,1200}     前进，动力 100%，1200 ms（后两个字段可省：默认 40 / 800）
{BASE+MOVE,left}                 原地左转（默认动力与时长）
{BASE+MOVE,backward,60,800}
{BASE+STOP}                      立即停
{BASE+LIGHT,blue}                全部灯变蓝（off/white/red/yellow/green/blue/deepblue/purple）
{BASE+LIGHT,off}
```

### 关键：它**不绕开**任何安全机制

命令全部经 `b220_baseboard_*` 转发，所以**动力/时长上限、600 ms 心跳、900 ms 超时兜底照旧生效**。

> 一个绕开安全机制的测试通道，测的就不是要出货的那套东西了。

### 实现要点

- 解析和"打印底座回复"合并在**同一个 RX 任务**里（都是"看 UART0 收到了什么"），
  且**必须整行处理** —— 这条线上既有底座的回复，也可能有我们自己的命令回显；
- **命令回显不算"底座回复"**：发送 `{BASE+...}` 时会置一个标志，RX 任务认出回显后
  **执行一次并抑制日志**，否则每发一条命令都会多出一行 `baseboard says:` 干扰阅读；
- 只在**以 `{BASE+` 开头**时才动作，所以正常的日志文本、底座的 `{AT+...}` 回复都不会误触发；
- 解析逻辑先在**主机上**用例覆盖过：`{BASE+MOVE,forward,100,1200}` / `{BASE+MOVE,left}`（默认值）/
  `{BASE+STOP}` / `{BASE+LIGHT,blue}` / `{BASE+LIGHT,off}` / `{BASE+MOVE}`（缺方向，拒绝）/
  `{BASE+X}`（未知动词）/ `{AT+Pon}` 与普通文本（忽略）—— 全部符合预期。

### 动力上限改为 100%

上机时默认 30% **轮子完全不动**，而参考文档明确提到"低转速启动扭矩不足"。所以：
**上限从 60% 提到协议的满值 100%**（MCP 工具的声明范围同步改为 `10..100`）。
防止乱跑的是**时长上限（3 s）**，不是动力 —— 如果实测发现太猛，`MAX_PWR` 是一个数字的事。

## 2.11a ★ 电机不动：**运动模式值全部写错了**（2026-10-11 上机）

### 现象（用户报告，telnet 日志）

```
Application: << % self.base.move...
b220-base-ctl: move: forward at 30% for 800 ms
b220-base-ctl: lights: on (sent)          <- 灯光正常
```
用户的判断是准确的：**"灯光正常，电机没反应"**。

### 为什么"灯亮"这条信息价值极大

它一次性排除了**物理层**：底座在线、供电域已解锁（`AT+Pon` 有效）、波特率/接线正确、
**我们的帧能被底座接受**。所以问题**必定在运动帧本身**，而不是在链路或供电上。
（这条推理链比逐一排查 UART/供电/接线快得多。）

### 根因：模式值

本文件第一版把方向写成 `forward=1, backward=2, left=3, right=4` —— **四个全错**。
参考项目的协议文档里真正的模式表是：

| 模式 | 行为 | 条件 |
| ---: | --- | --- |
| 0 | 原地向一侧转 | 转向角 **< 15** |
| 1 | 原地向另一侧转 | 转向角 **> 165** |
| 2 | **后退** / 后退左弯 | 后退，角度在左半区 |
| 3 | **前进** / 前进左弯 | 前进，角度在左半区 |
| 4 | 后退右弯 | 原始角度 > 99 |
| 5 | 前进右弯 | 原始角度 > 99 |

（`81..99` 归一化为 `90`；右半区内部会转成 `180 - angle` 并切到模式 4/5。）

正确映射：**前进 = 3、后退 = 2**（steer 90），**原地转 = 0 / 1**（角度取 `<15` 或 `>165` 的极点）。

> 教训：我把"模式"当成了方向编号，而它其实是**运动学模式**（前进/后退/转弯/原地转），
> 且**转向角参与决定模式**。参考文档里那张表就在同一份文件里，我第一次读时只看了帧的例子、
> 没读模式表。**帧格式对 ≠ 语义对** —— 这是这次上机的全部差距。

### 另一个容易误判的现象

修正前的底座构建里，**boot 日志中看不到运动帧**（只有一条 `{AT+Pon}`），
原因是**关掉 console 后帧不再回显到日志**。所以：
- 排查"帧到底发出去没有"要看 **telnet 日志**（`b220-base-ctl: move: ...`）而不是串口日志；
- 这也解释了为什么串口日志看着"什么都没发生"。

### 本次改动

- 方向表改为 `{名称, mode, steer}` 三元组：`forward(3,90)` / `backward(2,90)` / `left(0,0)` / `right(1,180)`；
- 运动帧的转向量**按方向取值**（原来固定 90，那是直行）；
- 日志更明确：`move: forward (mode 3, steer 90) at 40% for 800 ms`；
- **默认动力 30% → 40%**（参考文档提到"低转速启动扭矩不足可以提高最小动力"）；
- `left`/`right` 用**哪个极点**（0 还是 180）文档没写、**本机未验证** —— 两行代码里挨着，
  如果实测方向相反，**对调那两个角度**即可（注释里已写明）。

## 2.11 底座电机与灯光：控制入口 + 限速限时 + 超时兜底（2026-10-11）

### 之前的状态：三个函数**都没有调用者**

`b220_base_motion()` / `b220_base_stop()` / `b220_base_lights()` 早就实现了，但**没有任何地方调用**
—— 也就是说除了开机那次 `AT+Pon`，**电机和灯光根本没有入口**，这台机器动不了。

### 新增 `b220_baseboard.c/.h`：把"安全策略"和"协议"分开

| 机制 | 值 | 为什么 |
| --- | --- | --- |
| **动力上限** | `10..60`（低于 10 抬到 10，高于 60 压到 60） | 协议本身允许更大；但一台能被要求"满功率跑 30 秒"的玩具一定会撞到东西。**钳制并打日志**，不拒绝 —— 模糊的请求也应产生可预期的行为 |
| **单次时长上限** | `3000 ms`（默认 800） | 同上 |
| **心跳刷新** | 每 `600 ms` 重发一帧 | 参考项目实测**运动帧只有约 800 ms 有效期**（"运动帧有效期 800 ms"、"同方向保持 600 ms"）。不刷新的话一次 2 秒的移动会变成**一顿一顿的** |
| **超时兜底** | 超过 `900 ms` 没有刷新 ⇒ **发停止帧** | **最重要的安全机制**。参考项目明确警告"底座收不到停止会一直走"。这一条**同时覆盖所有失败原因**：丢网、任务卡死、这个文件自己的 bug —— **不需要预先想到是哪种** |
| 兜底阈值必须 > 刷新间隔 | 900 > 600 | 否则正常的心跳流会被自己的看门狗打断 |

**为什么用独立任务**：MCP 回调跑在协议任务上、**必须及时返回**，所以它只登记请求；真正的持续发帧在
本模块任务里做 —— 这也正是"停止"能够**打断一次进行中的移动**的原因。

### 灯光帧：原来的实现是错的，现在与参考**逐字节一致**

原实现发的是 `AT+CMD=(9,1,0,1),(0,0,0,0,0),(7,colour,2000,1),(7,colour,2000,2),...`，
**错两处**：头值 `9` 是**纯运动掩码**（参考的灯效果用 `4`），而且第二个元组应是**五字段控制元组**、
不该被当成灯图案的一部分。**大概会被底座直接忽略。**

现在照参考项目**实测过的**测试页帧复制：

```
ours(红) : AT+CMD=(5,1,4,1),(255,0,0,0,0),(7,1,2000,1),(7,1,2000,1),(7,1,2000,2),(7,1,2000,2)
参考实测 : AT+CMD=(5,1,4,1),(255,0,0,0,0),(7,1,2000,1),(7,1,2000,1),(7,1,2000,2),(7,1,2000,2)
IDENTICAL: True
```

颜色表（参考的实测值）：`0` 白、`1` 红、`2` 黄、`4` 绿、`5` 蓝、`6` 深蓝、`7` 紫；**关灯是另一条帧**
（`(5,1,4,1),(0,0,0,0,0),(7,0,0,1)...`，把时长和动力清零），不是某个颜色索引。

### 入口：三个 MCP 工具（大模型可调）

| 工具 | 参数 | 说明 |
| --- | --- | --- |
| `self.base.move` | `direction`(forward/backward/left/right)、`power`(10..60，默认 30)、`seconds`(0.2..3.0，默认 0.8) | 走到时间为止**自动停**；工具描述里明确建议"短距离多次"而不是一次长距离 |
| `self.base.stop` | — | 立即停 |
| `self.base.lights` | `color`(off/white/red/yellow/green/blue/deepblue/purple) | 全灯 |

工具本身**很薄**：限速、心跳、超时都在 `b220_baseboard.c` 里，所以**无论谁调用**（包括以后加按键映射）
这些保护都生效，不会在某个调用点被漏掉。

### ⚠️ 尚未验证的部分（必须说清）

帧的**格式**已与参考实测帧逐字节比对通过，但**这台机器上没有试过真底座**：

- **左右方向对不对**：模式 3/4 分别对应左转/右转是参考项目的约定，**本机未验证**；
- **转向量 90 = 直行**（我用固定 90）、动力 1..100 的观感、灯的实际颜色 —— 都是参考的值；
- **第一次上机请把"90 往哪边转"当成未解问题**来测。

## 3. 音量键仍然"只存值"（未解决，且本轮未动）

按键现在正确了，但**音量不会变**，因为 `Zl38063AudioCodec::SetOutputVolume()` 按设计只写
NVS + UI 指示，真正的增益在 DSP 内部（`reg 0x0238/0x023A`，PART 3 §1.6）。

参考项目也没有解决这件事（它的音量键只驱动本地 UI/蜂鸣），所以**没有可抄的现成答案**。
要真正实现，得单独确认 `zl38063_dsp_set_volume()` 这条路的档位表（`0x0238/0x023A` 的
`-90 dB + vol` 编码，以及 `0x0494/0x049A` 的高低音量分支）—— 这是一件独立的事，建议在
按键长按行为验收通过之后再单独开一轮。
