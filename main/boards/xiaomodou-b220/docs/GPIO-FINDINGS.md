# B220 主板 GPIO 逆向报告

对象：`backup\esp32-16MB-full.bin`（明文固件，无加密）
目标：从固件里挖出 LCD / 按键 / LED / ZL38063 / TF 卡等外设的 GPIO 连接

---

## 1. 方法（可复现）

固件里没有直接写引脚号的字符串，引脚分布在**代码立即数**和**配置结构体**里，因此需要反汇编。

流程：

1. 从 `app-strings.txt` 里挑出设备自己的日志/断言字符串（例如 `lcd_init`、`GPIO_BTN_STATE_MAIN_UP`）；
2. 求该字符串在 DROM 中的地址；
3. **按字节解码 Xtensa 的 L32R 指令**建立「字面量地址 → 引用它的代码地址」索引
   （Xtensa 是 16/24/48 位变长指令，从任意地址线性反汇编会在字面量池附近失步，所以不能依赖 objdump 输出）；
   L32R 目标 = `((PC+3) & ~3) + (imm16 × 4) − 0x40000`（imm16 **按无符号**取）；
4. 用 `entry a1, N` 指令模式定位函数入口，从入口重新反汇编该函数（保证解码同步）；
5. 跟踪寄存器常量，提取每次调用的参数。

工具都在 `tools\`：

| 文件 | 作用 |
| --- | --- |
| `re_helper.py` | 段映射、字符串定位、**字节级 L32R 交叉引用索引**、定点反汇编、函数边界定位、字符串转储 |
| `callscan.py` | 全镜像扫描调用点并恢复常量实参 |
| `func_pins.py` | 单函数级引脚提取 |
| `find_board_cfg.py` | 用「时钟/采样率魔数」在数据段里搜配置结构体 |
| `make_disasm.py` | 生成干净可 grep 的全量反汇编（`backup\disasm\`） |

## 2. 确定结论

### 2.1 LCD（SPI，160×128）—— 高置信

配置结构体在 **DROM 0x3f401654**，共 28 字节：

```
0x3f401654: 02 00 00 00 | 22 21 20 1b | 15 16 00 00 | 80 96 98 00 | 00 00 00 00 | 01 00 00 00 | 01 00 00 00
            +0 = 2      +4  +5  +6  +7  +8  +9     +12 = 10 000 000  +16 = 0      +20 = 1      +24 = 1
```

- 引用者：`0x40203890`（LCD 服务初始化）——把 28 字节拷到栈上，随后创建一个 **160×128** 的显示对象
- 使用者：`0x40203554`（`spi_lcd.c` 的驱动，内含 `lcd_init` 日志）——调用 `spi_bus_initialize` / `spi_bus_add_device`

驱动里的字段用法：

| 结构体字段 | 值 | 用途 | **GPIO** |
| --- | --- | --- | --- |
| +4 | 34 | `spi_bus_config_t` 第 2 个引脚（MISO） | **34** |
| +5 | 33 | 第 1 个引脚（MOSI） | **33** |
| +6 | 32 | 第 3 个引脚（SCLK） | **32** |
| +7 | 27 | SPI 设备片选 CS | **27** |
| +8 | 21 | 配置为**输出**（DC 数据/命令） | **21** |
| +9 | 22 | 配置为输出 + **100 ms 复位脉冲**（RESET） | **22** |
| +12 | 10 000 000 | SPI 时钟 10 MHz | |
| +20 | 1 | SPI 主机号 | |

> **MOSI/MISO 顺序的判定依据**：ESP-IDF 的 `spi_bus_config_t` 里 MOSI 在前。若按 MISO 在前，
> MOSI 会落到 GPIO34 —— 而 **GPIO34 是只输入引脚**，不可能做 MOSI。所以可以确定
> **MOSI = 33、MISO = 34**。

**LCD 接线汇总：SCLK=32，MOSI=33，MISO=34，CS=27，DC=21，RST=22**（SPI 模式，10 MHz，160×128）

### 2.2 GPIO19 = 某颗芯片的复位线 —— 高置信

函数 `0x40124418`：

```
memset(&cfg, 0, 24)
cfg.pin_bit_mask = 0x80000      → 1 << 19
cfg.mode         = 2            → GPIO_MODE_OUTPUT
gpio_config(&cfg)
gpio_set_level(19, 0)
delay(10 ms)
gpio_set_level(19, 1)
```

由 `0x40124454` 调用，之后延时 500 ms 继续初始化。典型的**外设复位脉冲**（ZL38063 语音 DSP 或图灵 AI 模组）。

### 2.3 TF 卡 = SDMMC 模式，引脚由硬件固定 —— 高置信

- 固件里**只有 SDMMC 驱动**（`sdmmc_host.c` / `sdmmc_cmd.c` / `sdmmc_sd.c`），**没有 sdspi** 的任何字符串；
- ESP32 的 SDMMC **slot 0 固定占用 GPIO6–11**，而这 6 个脚正是 SPI Flash 的引脚，物理上不可用；
- 因此只能用 **slot 1**，其引脚由 ESP32 硬件固定：

| 信号 | GPIO |
| --- | --- |
| CLK | **14** |
| CMD | **15** |
| D0 | **2** |
| D1 | **4** |
| D2 | **12** |
| D3 | **13** |

（若工作在 1 线模式，只用 CLK / CMD / D0。固件里有「slot width set to 4 … using 1 line mode」的告警字符串，说明可能是 1 线模式。）

### 2.4 第二个 SPI 设备（ZL38063 语音 DSP 控制口）—— 中置信

函数 `0x40234f90`：`spi_bus_initialize(host=1 或 2, buscfg, dma)`，随后以 **400 kHz**（0x61a80）挂设备。

- 总线引脚来自调用者传入的结构体：**32 位字段在 +0 / +4 / +8**（与 LCD 的字节字段不同）
- **+12** 的字段被当作 GPIO 用：代码用 `(1 << n)` 生成 `gpio_config_t.pin_bit_mask`、`mode = GPIO_OUTPUT` —— 即 **DSP 的复位/使能脚**
- **+24** 是 DMA 通道号

该驱动的入口没有任何静态引用（运行时注册），所以暂时没定位到它的配置结构体，具体引脚号未取出。

## 3. 重要架构结论：电机与头尾 LED 不在 ESP32 的 GPIO 上

固件里有一个完整的**工厂测试菜单**（`3.LCD test`、`4.Power led`、`5.Key test`、`10.Charging test`、`11.SDCard` …）。
其中「Head led test / Tail led test / Left motor test / right motor test」的处理函数是 `0x40204c7c`、`0x40204cdc`、`0x40204d3c` …，它们：

1. 先在 LCD 上打印测试项文字（`call 0x402068f4`）；
2. 然后调用 `0x40204b48(index)` —— 该函数是一个 **跳转表**（表在 `0x3f4beb08`，`addx4` + `jx`），
   每个分支加载一条 **AT 命令字符串**：`AT+HLY`(0x3f4be241)、`AT+HLN`(0x3f4be248) …

也就是说：

- **头部 LED、尾部 LED、左/右电机全部在「底座板」上**，由底座的 MCU 驱动；
- ESP32 只是通过 UART 发 `{AT+HLY}` / `{AT+HLN}` / `{AT+LMY}` / `{AT+RMY}` / `{AT+MTO}` 这类命令；
- 同理，`AiwifiController.c` 表明**图灵 AI WiFi 模组也是独立芯片**，同样走 UART。

**所以「电机/头尾灯的 ESP32 GPIO」在硬件上并不存在**，问主板 GPIO 只能得到 LCD / TF / DSP / 按键 / 麦克风 / 充电检测 / 两路 UART。

## 4. 尚未确定的部分

| 外设 | 状态 | 卡在哪 |
| --- | --- | --- |
| 按键 | 未取出引脚 | TouchManager 把事件处理函数注册在函数指针表 `0x3f4307d8`，引脚由别处传入；按键扫描函数 `0x40234758` / `0x40234138` 的引脚是**函数参数** |
| 主板指示灯 | 未取出 | 同上，引脚来自运行时配置 |
| 麦克风 / I2S | 未取出 | 配置结构体未定位到 |
| 充电检测 | 未取出 | `INTR_GPIO_CHARGE_PLUG` 所在函数 0x40125031 附近只有日志，GPIO 在更外层配置 |
| 两路 UART（底座、AI 模组） | 未取出 | 固件里没有 `uart_set_pin` 字符串，引脚可能走另外的初始化路径 |
| ZL38063 SPI 引脚具体值 | 部分 | 已定位驱动与 400 kHz 时钟，缺配置结构体 |

**共同原因**：这些引脚大多是**运行时通过结构体/参数传入**的，不是编译进代码的立即数；而相关驱动又是运行时注册的，没有静态引用可以顺藤摸瓜。

## 5. 把它们挖完的三条路

1. **继续追调用链**（静态）——用 `tools\` 里的工具顺着 `call8` 往上找调用者，直到出现常量引脚。
   可以做，但需要多轮迭代（本报告已经用掉相当多轮）。
2. **运行时读取**（最快最准）——这些配置结构体在 RAM 里。只要能进工厂测试模式，
   或利用任何可用的调试通道 dump RAM，就能直接读出所有引脚。
3. **万用表实测验证**——先拿 LCD 的 **32/33/34/27/21/22** 当标尺：在板上找到 ESP32 模组后，
   用通断档量这几条线是否通向 LCD 排线/测试点。验证分析方法无误后，再按第 1 条继续推其它外设。

---

## 6. 一句话结论

**B220 主板上由 ESP32 直接驱动的外设引脚，目前确定的是：LCD（SCLK 32 / MOSI 33 / MISO 34 / CS 27 / DC 21 / RST 22，10 MHz SPI，160×128）、
SD 卡（SDMMC slot 1：CLK 14 / CMD 15 / D0 2 / D1 4 / D2 12 / D3 13）、以及 GPIO19 的外设复位线；
电机和头尾 LED 在底座板上走串口 AT 命令，不占 ESP32 GPIO。**
